## Contribution and mechanism

The useful contribution is an evaluation framework for **experience-conditioned performance across ordered interactive tasks**, accompanied by a simple inference-time ensemble. It does not demonstrate a general solution to lifelong learning or catastrophic forgetting.

The benchmark contains 1,396 tasks: 500 Database (DB), 500 Operating System (OS), and 396 Knowledge Graph (KG) tasks (§4, pp. 4–5). DB uses MySQL, OS disposable Ubuntu containers, and KG a constrained interface to SPARQL-backed operations. DB and OS tasks are generated using DeepSeek-R1; KG tasks derive from GrailQA S-expressions. Task success is assessed through query-result comparison, database-state hashes, OS evaluation scripts, or graph-query outputs. The OS verifier's exit code is the evaluation script's result, not simply whether the agent's command exited successfully (Appendix A, pp. 12–16).

Skills annotate tasks: 22 SQL constructs, 29 shell commands, and seven graph operations. Relatedness is the harmonic mean of each task's shared-skill proportion (§4.1, p. 4). For skill sets A and B, this reduces to `2|A∩B|/(|A|+|B|)`, with zero assigned to no overlap. This symmetric Dice similarity measures shared labels; it does not establish directional prerequisite relationships or causal skill transfer. Common operations such as SELECT can dominate overlap without explaining which example will help.

The controller serializes tasks and retains completed sessions; callbacks can modify a new task's interaction history using prior sessions (Appendix B.1, pp. 17–19). The baseline inserts recent **successful trajectories** into prompts (§6.1, p. 6). This is external-memory, in-context adaptation, not gradient replay or backbone training. Despite the introduction's “persistent environment states” language, DB tables are cleared between tasks and OS containers replaced (Appendix A.1–A.2). Agent experience persists; task-side changes are deliberately isolated.

Group self-consistency divides historical examples among several prompts, extracts one action from each model response, and votes on the resulting actions (§6.5, Fig. 4, pp. 8–9). The figure shows action voting before execution. Its benefit requires useful, sufficiently diverse demonstrations and aggregable actions. Exact action equivalence, tie-breaking, and invalid-vote handling are not specified sufficiently in the paper to reconstruct a faithful implementation.

## What the experiments support

Reported task success rates illustrate substantial heterogeneity (Tables 2–3, p. 7):

| Model/environment | No replay | Selected replay result | Implication |
|---|---:|---:|---|
| Llama-3.1-8B, DB | 19% | 78%, 64 examples | Large gain in this setting |
| Llama-3.1-8B, OS | 43% | 50%, 4–16 examples; 42%, 32 | More history can regress |
| Llama-3.1-8B, KG | 28% | 35%, 1 example; OOM at 16 | Long trajectories constrain replay |
| Qwen2.5-32B, DB | 82% | 71%, 4 examples | Strong baseline harmed by replay |
| Llama-3.1-70B, DB | 81% | 90%, 64 examples | Backbone matters substantially |

Table 6 is a separate comparison: Llama-3.1-8B DB improves from 61% with 16 examples in one group to 75% with 16 groups; listed average input length falls from 17,874 to 2,888 tokens (p. 9). KG changes from 32% to 34%, with 56,409 versus 11,002 tokens. These are useful demonstrations of a context-length/ensemble tradeoff, not universal benefits: with four DB examples, splitting Llama's input into four groups reduces success from 63% to 59%.

**Retention is asserted more strongly than measured.** Cumulative task reward (§3) and aggregate success (§6) do not show whether old skills survive intervening learning. There is no reported old-task performance matrix, repeated delayed retention probes, or controlled forward/backward transfer analysis. Successful examples may teach output formatting or reveal familiar query templates. Without unrelated demonstrations, format-only demonstrations, and held-out skill combinations, these explanations remain entangled with skill acquisition. Selecting OS tasks because simpler tasks showed little replay benefit (§4.3) also conditions the dataset on the method being evaluated.

**Grouping's resource claim needs qualification.** The table reports average input tokens, not total compute, latency, or measured peak GPU memory. If a shared prompt has B tokens and all demonstrations total L, splitting across G calls yields approximately `G·B + L` input tokens instead of `B + L`, before repeated outputs and interaction history. Smaller calls can reduce per-call context requirements and attention cost, but total billed tokens can increase; concurrent groups can also replicate working memory. No equal-inference-budget ordinary self-consistency baseline separates grouping from additional model samples.

**Reproducibility and numerical provenance are incomplete.** Tables omit uncertainty intervals and repeated-order/seed statistics. Fixed seeds and containers alone cannot guarantee deterministic external model inference. Table 5's “# Task” column lists 19,114 two-action KG tasks despite the benchmark's stated 396 KG tasks; these may describe a source pool, but the table does not identify its evaluation denominators. Table 6's ungrouped Llama DB accuracy at 16 examples is 61%, versus 75% in Table 2; KG at 16 is executable there despite Table 2's OOM. Different configurations could explain this, but the paper does not reconcile them. Consequently, comparisons should stay within a table, and small gains should not be treated as significant.

**The appendix weakens confidence in label and failure explanations.** In C.2, Case 11 asks for three files with permissions and delays but labels `rm -f` on those files as “Ground Truth Action” (p. 27, visually verified). Several neighboring examples likewise appear to label initialization commands as solutions. This may be a presentation/export mistake; it does not establish that deployed task verifiers are wrong. More decisively, D.1.2 incorrectly says MySQL `LIMIT 2, 5` differs from `LIMIT 5 OFFSET 2` (p. 33, visually verified); they are equivalent. D.1.1 attributes failure to an initial incorrect query even though its displayed trace later corrects the query and submits the returned result (pp. 31–33), without identifying why that final answer fails. Appendix D's distinction between task outcome and termination status is valuable, but its individual causal diagnoses need independent checking. Automatic comparison verifies agreement with a reference, not the reference's correctness or the explanation of a failure.

## Mapping to the verified implementation

**Already implemented:** Navi has persistent, behaviorally consumed memory. [tokmem.c](../../../memories/src/tokmem.c) `crystallize_online:1600`, `index_associations:2536`, and `query_memories:5631` learn token structure/links and retrieve through bounded cue-derived association expansion (I02). [DecisionStateMachine.php](../../../src/Core/DecisionStateMachine.php) `start:134–191` performs intention-conditioned `memory.search`, limits results to eight, and supplies retrieved content to a model proposal (I04/Q03). This is a meaningful experience-to-action context route, although it does not establish complete-trajectory replay or a learned skill-overlap selector.

**Partially analogous mechanisms:** [ExecutiveCore.php](../../../src/Core/ExecutiveCore.php) `enqueueConsolidation:3159` and `integrateConsolidation:5020` implement guarded episodic-to-semantic synthesis; old examples are limited comparison-only evidence, not representative trajectory replay (I08/Q16). [ProceduralMemory.php](../../../src/Core/ProceduralMemory.php) `observe:399` compiles repeated verified adapter shapes after three successes, while `compose:983` supports bounded supplied sequences (I08/Q29/Q36). These are substantive learning mechanisms worth evaluating separately. They are neither the paper's prompt demonstrations nor unrestricted Bash/SQL agents: I05 verifies four installed adapters, with terminal decisions restricted to learning/grounding.

**Evidence available, but insufficient by itself:** ActionTrace, ActionExecution, ProcedureRun, and DecisionCycle retain linked execution metadata (Q29). Full observation reconstruction is not guaranteed: `ProceduralMemory::completePendingLook:1110` records output digests/byte counts in the observed projection, and `ExecutiveCore::rememberLook:4410` stores bounded excerpts (Q53). Successful adapter verification is also narrower than satisfying an intention's task goal (I05/Q36).

**Absent within inspected paths:** `ExecutiveCore::computeMetricVector:7994` supplies operational proxies, not independently verified lifelong competence (I10). No old-task behavioral gate was found in consolidation integration/publication (Q17). No aggregate ordinary-worker input-token check was found across `enqueueWork:6318` and client assembly, despite real component limits (Q11). These scoped absences justify measurement and context-budget experiments, not a claim that Navi lacks memory.

**Targeted evaluator/replay answer (Q58):** The master's additional search of production `src/bin/supervisor` PHP/Rust/Python/shell paths found no separate chronological reset-task evaluator with persistent memory, frozen-memory controls, and held-out old-task probes, nor a complete-successful-trajectory demonstration selector or grouped voting consumer. `DecisionStateMachine::compare:682` aggregates stored cycle outcomes by model; it does not execute evaluation tasks or remeasure retention. This resolves the requested implementation question within that search scope. External research assets remain unverified rather than ruled out.

## Prioritized recommendations

**P0 — Establish an independently scored chronological evaluation before changing production learning.** Build an isolated research harness around the verified decision/procedure boundaries and Q29's identifiers. Start with tasks expressible by installed adapters; using the original DB/OS/KG domains requires separate sandbox environment adapters and reviewed reference answers. Record task/order/version, model settings, skill tags, complete observations, termination reason, and independently checked goal outcome. Preserve agent memory across task resets, and compare against a fixed initial-memory branch. Add delayed, non-training probes of old skill families and novel combinations, across multiple task orders.

The main cost is trustworthy validators, complete capture, and isolated reproducible state. QMEM matters: `RANK_RECORDS` is candidate-read-neutral but still learns query links, so evaluation probes can change the learner unless run on disposable branches or an explicitly verified frozen path. Q17's checkpoint is a persistence barrier, not a restore image. A proposed adoption criterion is a positive lower 95% confidence bound for paired held-out improvement, estimated across independent task-order runs, and no old-family decline greater than two percentage points after new experience. These thresholds are recommendations, not paper results; failure rejects a lifelong-improvement claim even if memory count and proposal uptake rise.

**P1 — Compare bounded experience selection with controls that isolate the mechanism.** At a research wrapper around `DecisionStateMachine::start` retrieval and `ExecutiveCore::enqueueWork` assembly, compare current native recall, recent successful demonstrations, skill-overlap/diversity selection, and source-linked compressed demonstrations. Match total backend-token budgets and include no-history, format-only, and unrelated-history controls. Use a shared chronological archive first to isolate selection, then repeat with each policy's own online successes; otherwise better policies receive better replay pools and obscure the selection effect. Skill labels belong initially in the harness, not assumed existing memory metadata.

Dependencies are complete trajectories from P0 and the backend tokenizer; native memory-token counts are not interchangeable with model-token counts (Q11). Reserve output space and reject oversized assembled input explicitly. Report task success by overlap and trajectory length, total tokens, latency, and context failures. Reject the selector if its improvement disappears against format-only/unrelated controls, fails on unseen skill combinations, or exceeds the fixed budget. Evaluate compression against raw demonstrations: shorter context is useful only if task-relevant constraints and outcomes survive.

**P2 — Experiment with small grouped proposal ensembles only if P1 exposes a context bottleneck.** Use two or four groups in an isolated controller before the existing candidate validation/dispatch boundary (`DecisionStateMachine::integrate`, Q03). Canonicalize votes by installed adapter and typed arguments, define invalid votes/ties, and execute only the selected, normally validated proposal. This requires an additional voting controller; the existing deterministic candidate score is not majority voting. Correlated, confidently wrong proposals remain wrong.

Compare grouped distinct histories against repeated sampling of the same bounded history at equal model-call and total-token budgets. Measure independently verified task success, total input/output tokens, wall time, and actual peak memory with scheduling disclosed. Reject adoption unless grouping improves the measured success/resource frontier; lower average prompt length alone does not pass. This is a conditional inference experiment, not a reason to replace the memory engine or relax action contracts.

## Verdict and coverage

**Adopt the chronological evaluation principle; experiment with bounded replay; defer grouped voting pending controlled cost evidence.** The consequential next step is measuring whether Navi's existing learning mechanisms improve later behavior without degrading old competence. The paper motivates that question more convincingly than it answers it.
