## Contribution and mechanism

The useful contribution is an explicit **rule for admitting progress into persistent task state**: an executor's completion claim cannot itself establish completion. LongHorizon-Harness combines this rule with task decomposition, fresh execution contexts, and repeated environment inspection. This is a systems architecture with empirical evaluation, not a learning algorithm or a theorem about reliable reasoning.

The Manage–Execute–Audit loop separates three roles (§§2.1–2.4, pp. 4–6):

- The **manager** retains the original task, structured requirement/artifact/fact records, and accumulated audit reports. Records have completed/pending/blocked/untrusted status and supporting evidence references. The manager has no environment tools. It issues one bounded contract containing a goal, acceptance criteria, constraints, and relevant prior evidence, or chooses done/blocked/ask.
- A **fresh-context executor** receives that contract and selected evidence, uses its assigned GUI or CLI tools, and returns an outcome report. Its raw trajectory and reasoning do not carry into the next execution context.
- A **fresh-context auditor** receives the task, contract, state, selected prior audits, and executor report. It independently inspects the resulting environment, returning completion status, integrity status, verified findings, and remaining gaps. Only clean audit evidence can justify a completed record.

Equations (1)–(3) specify these interfaces; they do not prove that the manager's update function preserves truth. The AgentAdapter retains each backend's native agent loop. Defaults allow 25 rounds, with 1,800 seconds per executor and 300 seconds each for manager/auditor (p. 7).

The mechanism assumes that requirements can be decomposed into observable predicates, the environment exposes adequate evidence, and auditors correctly interpret both. Although executor context is bounded, the manager receives **all accumulated audits** (§2.2). No bounded audit-history compaction policy is specified; relocating history does not eliminate its growth.

## Evidence and its limits

| Evaluation | Reported change | What the comparison supports |
|---|---|---|
| WeaveBench, 114 tasks, Qwen 3.7-Plus/Claude Code | PassRate 51.8% → 80.7%; mean score 0.702 → 0.835 | Strongest broad matched-backbone/backend evidence for the combined harness; both in-house configurations use root privileges (Table 1, pp. 6–7). |
| Terminal-Bench 2.1, Qwen/Claude Code | Success 69.7% → 77.2% | Transfer to pure CLI tasks; three trials per task, shared model settings and five-hour trial timeout (Fig. 3, p. 8; §A.3, p. 19). |
| OSWorld 2.0, 108 tasks, Qwen | Binary 2.8% → 8.3%; partial 21.5% → 35.2% | Combined harness **and tool-pool change**: official single-action GUI baseline versus hybrid GUI+CLI (Table 2, p. 7; §A.2, p. 18). |
| OSWorld Opus 4.7 subset, 34 tasks | Binary 20.6% → 35.3%; partial 55.8% → 66.9% | A second backbone, with the same GUI-versus-hybrid confound and an unexplained subset-selection procedure (Tables 3/5, pp. 8/19). |

Two reporting details materially affect interpretation. First, WeaveBench “PassRate” means **score ≥0.8**, not complete satisfaction of every requirement (§A.1, p. 18), despite the main text's “fully passed” wording. Second, the abstract/introduction give Opus binary results of **20.0% → 34.3%**. Table 5 instead contains 7/34 versus 12/34 exact successes, agreeing with Table 3's **20.6% → 35.3%**. Recalculation of that published table also gives eight new successes and three lost successes. These are arithmetic checks of reported data, not new trials.

Cost is consequential. Figure 5 (p. 9) gives approximately 12.0M → 27.4M total tokens/task on WeaveBench, 28.9K → 104K output tokens/task on OSWorld, and 4.6M → 3.5M total tokens/task on Terminal-Bench. Auditing consumes 19.4%, 24.8%, and 38.1% respectively (§3.3, pp. 9–10). The manager's small token share does not establish low total overhead. Terminal-Bench's improvement with fewer tokens is encouraging, but token totals are neither dollar costs nor end-to-end latency. The 17-game subset further shows opposite cost changes for Opus and Qwen (Table 4, p. 11).

There is **no component ablation** separating audit admission, fresh contexts, explicit state, decomposition, and repeated recovery. Matching the backbone does not isolate task-state management as claimed on p. 7. WeaveBench also lacks an equal-total-compute baseline. Terminal-Bench weakens a blanket “just more tokens” explanation, without identifying which component causes the gain. Figure 3's Luna result is 83.1%, but its 75.7% baseline is externally reported, unlike the in-house Qwen pair. Official WeaveBench leaderboard comparisons additionally differ in privileges.

No confidence intervals or repeated-run variability are supplied for the main aggregates; only Terminal-Bench explicitly reports three trials. WeaveBench uses an Opus 4.7 trajectory-aware judge (§A.1, p. 18), so its scores also depend on model judging; judge robustness is not evaluated. Qualitative cases are selected illustrations, not randomized mechanism interventions. Appendix B acknowledges regressions: WeaveBench Desktop mean score falls despite higher threshold pass rate, and several Terminal-Bench analytical categories worsen (Tables 6/9, pp. 20/22). Overlapping tags and small categories cannot independently establish which task properties cause benefit.

## Where the reliability claim remains conditional

Fresh context removes one route for anchoring, but not shared model errors. All three roles ordinarily use the same backbone (§3.1), and the auditor sees the executor's report. A confidently misinterpreted contract can therefore survive every role; the paper explicitly recognizes this for hidden thresholds and ambiguous evaluation semantics (§B.2, pp. 20–21). No auditor false-acceptance rate, integrity-monitor detection rate, or calibrated abstention result is reported.

Final-state evidence also cannot generally establish **how that state was reached**. The document-style example requires a prescribed LibreOffice workflow; correct final XML alone cannot prove that workflow occurred (Fig. 8, p. 13). The spreadsheet example more persuasively demonstrates why pre-repair evidence must be captured before it becomes unavailable (Fig. 9, p. 14). Process constraints need trusted transition evidence, not just another look at the final artifact.

The claimed read-only auditor is a substantive authority boundary (§2.4, p. 6), but this PDF does not detail the monitor's protected-state coverage, transient-change detection, or false positives. Figure 20 (p. 29) shows a final independence check that renames the reference binary and deletes/regenerates output. Its displayed final-delivery block does not establish which role performed those mutations or whether a disposable copy was used. This is an implementation ambiguity, not proof that the auditor violated its restrictions. It illustrates why “verification” and “non-mutating execution” need separate specifications.

Finally, keeping only verified facts in active execution context should not mean deleting uncertain hypotheses or original evidence from the system. Exploratory cognition needs provisional alternatives. For Navi, audit status should govern **task-progress authority**, while hypotheses and diagnostic traces remain explicitly non-authoritative. The paper offers no evidence about autobiographical continuity, learning across tasks, or consciousness.

## Mapping to verified Navi-Brain mechanisms

**Already implemented:** Durable intentions with textual success/release conditions, working-memory slots, leased work, bounded model invocations, action traces, and a narrow observe→reason→execute→verify loop exist (I03–I05/I10). Relevant seams are `src/Core/DecisionStateMachine.php::start:34`, `::integrate:254`, and `::finishVerified:743`; `src/Core/ExecutiveCore.php::enqueueWork:6318`; and `src/Core/WorkingMemory.php::contextForWork:223`. `src/Core/CodexSparkWorker.php::invokeModel:130` launches an ephemeral, proposal-only worker. Navi is already externalizing continuity; it does not need a wholesale conversion from one perpetually growing model conversation.

**Partial correspondence:** The registry at `src/Core/ProceduralMemory.php:41` supplies four installed adapter contracts and narrow verifiers, including `machine.look` exit-code success and consolidation provenance (I05). These are useful operational checks, not verification of arbitrary task requirements. Installed terminal adapters are classified as grounding/learning; this registry is not the paper's general editing/build/GUI executor. Those classifications do not restrict the actual effects of model-selected shell commands, as Q65 qualifies below. Q54 establishes that decision `current_plan`/`decision_basis` are published **before execution**, while later `finishVerified` records the action result without enforcing a recurrent audited task-state update. Persistent prose is not the paper's completed/pending requirement ledger.

**Consequential missing admission gate:** Q05/Q67 verify that `ExecutiveCore::enqueueCompletionCheck:9814` asks a separate model job to judge a success condition from up to eight memory excerpts. It does not independently inspect the current environment. `::integrateCompletionCheck:9877` can accept `intention_complete` at confidence ≥0.7; it writes canonical status **released** while emitting/returning **completed**. Direct `::closeIntention:1471` also needs no independent audit. Thus “a separate judge already exists” would obscure the missing evidence guarantee and inconsistent closure semantics.

**Absent within the stated search:** Q67 found neither an independent fresh-context environment auditor gating a requirement/artifact/fact ledger nor a generic before/after task-artifact guard that rejects mutation-tainted audit reports. Its scope covers completion, workers/adapters, relevant models, and existing integrity paths. Consolidation source hashes and PublicReflection publication hashes protect narrower contracts (I08/Q59), not arbitrary task environments.

**Authority and freshness need additional work:** Q65 traces model-selected shell text through `src/Perception/CommandSense.php::observe:66` to `bin/navi-senses::look:106`. The separate account and resource limits do not establish read-only filesystem/network effects. QMEM further shows that ordinary `searchMemory`/rank operations can mutate retrieval state. Q02/Q44 show that decision integration does not compare its saved workspace or goal revision against current state. An old, clean audit could consequently become stale before commitment unless a new version check is supplied. Deployed permissions and external audit infrastructure remain unverified.

## Prioritized recommendations and falsifiable evaluation

**P0 — Experiment with evidence-bearing task completion.** Add a proposed per-intention requirement/artifact/fact ledger around `ExecutiveCore::enqueueCompletionCheck`, `::integrateCompletionCheck`, and decision `finishVerified`. Each proposed status delta should name its requirement, originating action, evidence receipt, acceptance predicate, and goal/artifact revision. A deterministic commit rule should require satisfied predicates and clean, current evidence; unknowns remain pending. Preserve explicit user release as a distinct disposition and reconcile the existing released/completed mismatch. This follows directly from MEA's admission rule and reuses existing IDs instead of mistaking them for sufficient evidence.

The cost is a typed schema, evidence retention, and closure-path integration. Begin with inspectable artifact tasks and deterministic predicates; add model interpretation only where needed. In a future isolated evaluation, include plausible-but-wrong outputs, missing deliverables, changed requirements, and artifact replacement between inspection and commit. **Failure criterion:** any automatic completed transition without its required valid receipts, or any delayed receipt accepted against the wrong version. Also measure false blocking on genuinely satisfied tasks, so refusal cannot masquerade as reliability.

**P1 — Make audit observation enforceable before granting it completion authority.** Add a distinct audit work type beside existing `enqueueWork`/worker integration, backed by constrained environment inspectors. Provide task/contract/evidence locators, but exclude executor reasoning and generic workspace prose that could reintroduce its claims (I10/Q14). Use read-only snapshots or constrained APIs; execute checks that write temporary data against disposable copies. Reuse hashing patterns from consolidation/PublicReflection while defining a new artifact scope and trusted receipt producer. Do not designate unrestricted `machine.look` or learning retrieval calls as immutable auditors.

Dependencies include P0's receipt schema, sandboxed inspection, version binding, and protected capture of process evidence. Costs include another invocation, inspection latency, storage, and incomplete visibility into live applications. **Failure criterion:** an auditor changes protected state and its report remains admissible, accepts substituted/stale evidence, or certifies a process constraint solely from indistinguishable final state. Exercise these cases in disposable environments; no production audit action is proposed by this review.

**P2 — Establish whether a separate model auditor earns its cost.** Design an offline study comparing current Navi, the typed ledger with existing deterministic verifiers, and that ledger plus independent model auditing. Hold models, tools, privileges, fresh executor contexts, and total token/wall-time caps constant. Ablate auditor context isolation by exposing executor reasoning in a separate condition. Start with fixture/replayed artifact transitions; full GUI/CLI workflows require a separate authorized executor harness. Include recoverable stalls, pre-repair evidence requirements, misleading artifacts, hidden acceptance conditions, and short analytical controls.

Use independently scored final success, false completion, destructive regression, repeated failed actions, token cost per success, and measured wall time. Existing `DecisionStateMachine::compare:682` and thread metrics are instrumentation inputs, not independent task ground truth (I10/Q58); timestamps also need correlation beyond current stage proxies (Q02). Repeat paired tasks and report uncertainty at task level. **Failure criterion:** no resolved success improvement over the ledger-only condition under the agreed budget, or gains accompanied by worse false completion or integrity violations. These are proposed studies; none was performed here.

## Verdict and coverage

**Experiment.** Adopt the architectural requirement that task progress needs explicit evidence, then test whether a separate model auditor improves on deterministic verification. The most consequential next step is an isolated completion-ledger prototype that exposes Navi's present confidence-based closure gap. The paper supports evaluating that boundary; it does not justify installing three model roles throughout cognition or promising its benchmark gains will transfer.
