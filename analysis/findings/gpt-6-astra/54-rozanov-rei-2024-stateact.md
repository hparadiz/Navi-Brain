## Assessment

**Experiment with explicit task-state summaries; retain existing goal reminders as the baseline.** StateAct supplies credible evidence that changing the information generated before an action can improve a language agent without parameter training. It does not establish that every agent benefits from repeating both its goal and state, that generated state is trustworthy, or that the method solves bounded-memory continuity. Navi already persists intentions, supplies decision prompts with success conditions, and carries working context across calls. Its relevant experiment is the incremental value of a compact, evidence-grounded task-state representation inside that existing machinery.

## Mechanism and assumptions

StateAct augments a ReAct-style observation–thought–action trace with a repeated goal and explicit current-state fields. One model call generates these fields together with the next action; the wrapper extracts and executes only the action. Few-shot demonstrations show the desired pattern. For Alfworld, state includes location and inventory; Webshop uses page location and selected product attributes (§§3–3.3, pp. 3–4; Appendix J, pp. 14–17).

Appendix K, p. 17, writes the output as `c_t = (g_0, s_t, r_t, a_t)` and the policy as `π_contextual(c_t | o_t, c_{t−1}, …, c_0, o_0)`. This formalizes an augmented textual history, not a learned transition model or a proof that `s_t` is a sufficient statistic. The goal is assumed fixed throughout an environment. State is inferred from previous actions and observations; a probabilistic belief distribution, explicit unknown values, and acceptance checks on generated state are not supplied by this mechanism.

My interpretation is that repeated task variables provide accessible intermediate representations that can reduce reconstruction errors before action selection. That explanation is plausible, but recency, added generation, demonstration annotation, and history truncation remain alternative contributors. The method retains historical context in its formulation; replacing the entire history with the latest state would be a separate, unvalidated compression proposal. It provides no evidence about consciousness or persistent subjective identity.

“No additional training data” means no extra training corpus or parameter updates: humans still annotate the existing successful demonstrations with goal/state information. The demonstrations become substantially longer, from 590–935 to 807–1,458 tokens per Alfworld example (§4.4, p. 5). StateAct therefore has an annotation and context cost even though it requires no extra model call per environment turn.

## Evidence and limitations

The study evaluates text-only Alfworld, Webshop, and Textcraft, with 134, 100, and 100 test environments respectively; action limits are 50, 15, and 40. Five locally run models span Mistral, Qwen, and Gemma, with three additional API-served models evaluated on Alfworld. Decoding is greedy (§§4–6, pp. 4–7).

| Comparison | Reported result | Interpretation |
|---|---|---|
| Five-model Alfworld average | ReAct .58 → full StateAct .66 | +8 percentage points in main Table 2, p. 7 |
| Five-model Webshop average | .26 → .28 | +2 points; materially smaller than a seven-point claim |
| Five-model Textcraft average | .23 → .31 | +8 points, approximately 35% relative using rounded averages |
| GPT-3.5 Alfworld | 63.70% → 77.04% | +13.34 points; §5.1 and Table 7 |
| Textcraft with ADaPT | .40 → .45 average | +5 points, approximately 12.5% relative; Table 4 |

The headline percentages mix comparisons and should not be read uniformly as percentage-point gains. Table 2 shows improvement in 13 of 15 model/environment combinations, but Qwen-7B worsens on Webshop (.19 → .12). With ADaPT, the full StateAct average improves while Qwen-14B and Qwen-32B each decline by two points. This is evidence of compatibility with one extension under one configuration, not universal compositional benefit or equal-compute superiority (§5.2; Table 4, p. 7).

The factorial ablations are more informative than the headline. On Alfworld, goal+thought+action averages .65 versus .66 for the full method: adding state contributes little on this aggregate. On Webshop, state+action reaches .31, exceeding both ReAct's .26 and full StateAct's .28; adding thoughts to state+action reduces the average to .18. On Textcraft, state+thought+action reaches .34 versus .31 with the additional goal reminder (Table 6, p. 8; Tables 9–10, p. 18). These interactions argue for task/model-specific configurations. They also contradict a blanket reading of §6.4 that thoughts always harm Webshop: adding thoughts to goal+state+action changes .29 to .28, while ReAct still exceeds action-only .19.

State tracking achieves approximately 88% agreement with a heuristic tracker in Alfworld, versus .72 for state+action, .85 with thoughts, and .78 with goals (Figure 6, p. 8). The tracker updates variables when an action is accepted by the environment, rather than merely assuming requested actions succeeded (§6.3, p. 7; Appendix F, p. 13). This is useful behavioral measurement. It is not an independent full-world oracle, calibrated uncertainty estimate, or causal demonstration that state accuracy mediates task success. The appendix does not fully specify field aggregation and scoring rules; roughly 12% disagreement also makes unvalidated state unsuitable as authoritative executive data.

Efficiency evidence is suggestive. Table 5 reports 31.49 average steps for ReAct and 19.11 for full StateAct, with intermediate ablations at 20.09–23.76. However, Figure 5 groups tasks by the number of steps the evaluated agent actually takes. Those groups are affected by the method and contain different tasks: §6.2 explicitly reports 24 ReAct episodes but only six StateAct episodes in the 40–50-step bucket. Comparing success within those buckets does not isolate intrinsic long-horizon difficulty. Appendix G acknowledges difficulty in constructing a fair optimal-length reference. Aggregate steps can reflect fewer capped failures as well as shorter successful solutions. The approximately $8-per-Alfworld-run comparison is a narrow cost report, not a general token or latency advantage (p. 7, footnote 6).

Several local-source issues limit exact replication and interpretation:

- **Conflicting results:** Main Table 2 reports Gemma's full-StateAct Alfworld score as .68 and the five-model average as .66. Appendix Table 8 reports .76 and .68, and labels the dataset as 135 environments rather than 134. This changes whether Gemma improves over ReAct's .71. Both renderings were visually checked; neither is silently corrected here.
- **Formatting confound:** Appendix I/Table 7, p. 14, reports 77.04% → 58.52% when StateAct uses “JSON.” The displayed example contains Python `None` and lacks a comma between the thought and action fields, so it is not valid JSON. This does not prove the executed prompts had those defects, but it prevents treating the result as clean evidence against valid schema-constrained output.
- **Context handling:** Appendix E.1, p. 13, visibly slices `prompt[-self.max_model_len:]` before tokenization. As displayed, this bounds characters rather than tokens and can discard early goal/examples. Without the executed artifacts, its actual contribution is unresolved. This matters directly to the claim that repetition repairs long-context reasoning rather than compensating partly for input truncation.
- **Experimental uncertainty:** Main comparisons use single greedy runs without confidence intervals or prompt-rephrasing robustness checks. Reused trajectories improve comparability, but §4.4 also mentions correcting ReAct prompt errors without a correction-only ablation. Table 3 names GPT-4o-mini in its rows but a GPT-4o identifier in its caption. Cross-paper state-of-the-art comparisons do not establish matched budgets or identical environment versions; Appendix A.2.1 discusses an Alfworld command-version change.

The English-only, three-environment scope and reliance on human annotations are acknowledged in §9, p. 9. The paper's argument that fine-tuning does not permit generalization (§2.2, p. 2) is broader than its experiments support. These qualifications leave a useful prompt-design result, with weaker support for universal superiority or a specific causal account of long-range reasoning.

## Mapping to Navi-Brain

**Already implemented:** [DecisionStateMachine.php](../../../src/Core/DecisionStateMachine.php), `start:38, :195–208`, supplies the selected intention's title, next action, and success condition. It snapshots working memory, observes pending sensory events, and retrieves long-term evidence. [ExecutiveCore.php](../../../src/Core/ExecutiveCore.php), `enqueueWork:6360–6420`, additionally supplies eligible workspace and background state. These are verified goal/context reminders, although they are not StateAct's generated goal echo (I04; Q14; Q44).

**Partial functional overlap:** [WorkingMemory.php](../../../src/Core/WorkingMemory.php), `publish:122`, `snapshot:201`, and `contextForWork:223`, already implements persistent, scoped, provenance-bearing context. Decision integration publishes `current_plan` and `decision_basis`, and prior action outcomes can enter workspace context (I03; Q52). These mechanisms are stronger persistence than an ephemeral trace, but persistence alone does not require correct reconstruction of the current task situation. The reference establishes no general source-linked reconciliation contract for those plan/basis writes (Q52).

**Absent within inspected boundaries:** Decision integration does not compare its saved workspace checksum against current state, and no goal-contract revision check was found at integration/dispatch (Q02; Q44). Existing active-intention checks, procedure-generation constraints, and dispatch fencing remain real protections. They do not establish that a queued proposal reflects newly changed goal text or observations.

**Specific missing state contract, now verified:** The master's Q54 follow-up found no required `task_state`/`state_delta`, previous-action link, or outcome-validated recurrent task summary in `DecisionStateMachine` and its immediate context compilers. Its content schema requires `current_plan`, `decision_basis`, and candidates (`:195–208, :278–298`). Plan/basis slots are published before execution (`:300–334`); `finishVerified:743` records outcomes without an additional model state updater. Previous prose can remain available through working memory, but its meaning is not constrained to represent current task state. This is a bounded negative finding, not a claim that Navi lacks state or outcome persistence.

Transfer belongs at the model-proposal/context boundary. Navi's installed terminal adapters are observation and consolidation, not a household or shopping action repertoire (I05; Q03). Its sensor `ForwardModel` is also a different mechanism: one-step sensory forecasting is not StateAct's textual current-task reconstruction (I07). Finally, `operation_drift` measures operation-label violations, not semantic departure from the goal, and cannot validate StateAct's goal-adherence claim (Q44).

## Prioritized recommendations

**1. Evaluate incremental state and goal generation before production adoption.** At `DecisionStateMachine::start` and its proposal schema, compare the current prompt against added goal echo, added compact task state, and both. Keep the existing canonical goal block and action contracts in every arm. Use a bounded state description covering task-relevant resources, completed prerequisites, latest accepted outcome, and unresolved facts; do not introduce a second memory subsystem. This directly tests the paper's two contributions against Navi's stronger baseline.

Dependencies are an isolated evaluation setup, independently scored workflows compatible with installed adapters, and evidence sequences containing failed actions, distractors, and delayed acknowledgments. Match model, observations, demonstrations, and budgets; include a control receiving equivalent factual input without generating a state summary. Measure terminal success, critical state errors, tokens, invalid proposals, and elapsed time. A proposed promotion threshold is at least five percentage points higher success with a paired 95% interval excluding zero, without increased critical-state error. An effect that vanishes against the factual-input control does not establish a benefit from generated state itself. These are proposed criteria, not observed results.

**2. Require evidence-grounded updates and freshness before trusting carried state.** This is an engineering extension motivated by the paper's 88% accuracy and fixed-goal assumption, not an evaluated StateAct feature. At integration and `WorkingMemory::publish`, associate candidate state changes with accepted action/observation identities, preserve explicit unknowns, and keep generated goal text subordinate to the current intention. Bind proposals to a digest/version of relevant intention and task evidence, then revalidate changes before publication or dispatch. Avoid comparing a global workspace checksum blindly: the decision path itself publishes workspace content during assembly/integration (Q02; Q52).

This requires field semantics, evidence linkage, and a bounded stale-proposal recovery policy. Evaluate failed-action acknowledgments, out-of-order outcomes, revised goals, and unrelated workspace updates. Fail the design if an unexecuted action's predicted effect becomes a confirmed state change, an obsolete goal controls dispatch, or unrelated context changes cause unbounded re-proposals. Compare with unvalidated state carry-forward to measure whether the protection reduces propagated errors at acceptable latency.

**3. Ablate representation and verbosity inside the existing typed boundary.** Q14 verifies schema-conforming worker output; retain that contract. Compare concise labeled state text within a typed field against valid structured state fields, keeping semantic content and token allowance comparable. Separately compare normal decision explanation with a short action justification. Appendix I warrants measuring formatting, while Tables 6/9/10 warrant measuring verbosity rather than automatically expanding it.

The cost is evaluation and parser/schema integration, not extra model training. Select configurations on a development split and verify them on held-out workflows and model variants. Reject a more elaborate representation if it increases parse failures, reduces held-out success, or uses more tokens without improving state accuracy or success. Do not remove typed validation because one malformed published “JSON” example performed poorly.

## Verdict and coverage

**Experiment.** The consequential next step is a controlled comparison of explicit task-state generation against Navi's existing goal/context prompts. Adopt neither universal goal repetition nor unrestricted prose state as executive truth. This paper supports a modest interface experiment; it does not justify replacing working memory, expanding action authority, or claiming a solved continuity mechanism.
