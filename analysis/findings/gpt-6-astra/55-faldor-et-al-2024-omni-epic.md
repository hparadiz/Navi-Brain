# OMNI-EPIC: Open-Endedness via Models of human Notions of Interestingness with Environments Programmed in Code

Maxence Faldor, Jenny Zhang, Antoine Cully, and Jeff Clune. **Local version:** arXiv:2405.15568v3, 14 February 2025; published as a conference paper at ICLR 2025. The repository filename retains 2024, but this review evaluates the revised 2025 paper. [Local PDF](../../../assets/papers/55-faldor-et-al-2024-omni-epic.pdf). **Reviewer:** GPT-6 Astra. **Implementation evidence:** [shared implementation reference](IMPLEMENTATION.md), snapshot 2026-09-06, HEAD `ee1590009d6fd4c48035c63e15b3896a585757d7`; static inspection by the implementation master, not runtime validation.

**Assessment.** Experiment with archive-conditioned generation of executable practice tasks, after establishing independent task-success checks. OMNI-EPIC provides credible evidence that foundation models can expand a simulator's task repertoire and use successful and failed attempts to guide a curriculum. It does not demonstrate indefinite capability growth, a generalist agent, or a reliable universal success oracle. Its most useful contribution to Navi is an experimental curriculum architecture, not evidence that persistent thought or growing memory already constitutes open-ended learning.

**Core mechanism and assumptions.** The search object is a task description plus executable environment code, rather than a vector of parameters inside a fixed level generator. Code specifies the simulated world, dynamics, reward shaping, termination, and a separate `get_success` predicate (§§3.1–3.6, PDF pp. 4–6). The implemented search remains inside PyBullet with existing robot interfaces; Turing-complete Python describes a potential representational ceiling, not a demonstrated ability to discover, verify, or efficiently learn every computable environment.

Each iteration selects an archive task and retrieves nearby successful and failed examples. An LLM proposes a learnable, interesting task; another generation step implements it and repairs execution errors. A post-generation model of interestingness compares the candidate with its own nearest archive neighbors before expensive training. This separates the examples used for inspiration from the examples needed to check duplication. A DreamerV3 specialist then trains, initialized from the successfully learned task with the closest embedding. Failure can trigger environment/reward revision; successes and exhausted failures become future context (§3, pp. 4–6; Appendix J, p. 105).

The documented settings retrieve five learned and five failed examples for generation and ten neighbors for post-generation assessment. Task and environment generation use Claude 3 Opus; the post-generation judge uses GPT-4o. Descriptions **and code** are embedded using `text-embedding-3-small` (Appendices J–L, pp. 105–110). These choices assume that textual/code similarity predicts useful skill transfer and that model judgments capture worthwhile novelty. Neither assumption follows from the embedding interface itself.

“Learning progress” here principally means prompting with successes/failures and requesting an appropriately challenging next task. It is not an explicit estimator of the slope of competence over comparable trials. Interestingness is also permissive: Appendix L.4 accepts novelty, creativity, entertainment, difficulty, **or** human usefulness, rather than requiring all of them (p. 110). The engineering contribution is the integrated search-and-learning loop, not a new mathematical definition of progress or intrinsic reward.

**Evidence and limits.** The empirical results support several different claims, which should remain separate:

- **Generative breadth:** the long run displays 200 iterations, excluding non-executable generations, while assuming generated tasks are successfully completed. Its attractive task graph demonstrates generated descriptions/environments, not 200 acquired skills (§4, pp. 6–8, Fig. 2). Checkmarks in this figure must be interpreted under that assumption. Highlighted examples were manually selected across the embedding space.
- **Actual learning:** five short runs train RL agents. The showcased run reports 16 completed tasks, six failures, and one rejected as uninteresting (§5, p. 8). R2D2 receives proprioception and 64×64 RGB observations and has six discrete actions. Appendix P adds examples with an Ant's eight-dimensional continuous action space (p. 126), broadening interface feasibility without establishing arbitrary embodiment or sim-to-real transfer.
- **Transfer:** Appendix G.1 compares five replications on 25 tasks under equal per-task training steps. Median success is 63.2% with transferred policies, versus 36.8% from scratch; reported intervals are 42.1–69.5% and 31.6–53.7% (p. 98). Figure 41 clarifies that the scratch comparison uses the same generated tasks (p. 104). This supports useful initialization on that task distribution. It does not measure one policy retaining all earlier capabilities or generalizing to a held-out task distribution.
- **Archive and interestingness:** three simulated-learning replications compare full OMNI-EPIC with no archive and with both interestingness mechanisms removed. Five RL replications compare progress metrics. Full OMNI-EPIC reportedly wins at Mann–Whitney p<0.05 (§6, pp. 9–10). Appendix G's illustrative ablations report only five learned tasks with uniformly sampled examples, seven without failed examples, and none after removing learning-progress instructions (pp. 98–101). Those latter examples lack the replicated quantitative support of the transfer comparison, and their generated task populations differ.

The metrics constrain interpretation. Diversity is occupied-cell coverage after jointly projecting task-description/code embeddings to two principal components. Multiple discretizations preserve the long-run trend, but short-run diversity differences are not consistently significant (Appendix I, p. 103). Semantic surface variation and code structure can increase this score without creating distinct useful skills. With only three long-run replications per method, significance also needs a disclosed exact/asymptotic and sidedness convention: an exact two-sided Mann–Whitney test with three observations per group cannot reach p<0.05. The paper does not supply enough detail to resolve that issue.

ANNECS-OMNI counts tasks satisfying learnability, solution, and model-assessed interestingness. Since the full method already filters for interestingness, this measure partly rewards its selection criterion; an independent judge is needed to establish externally valuable novelty. Appendix I also reports an advantage on ANNECS without the extra interestingness criterion, which prevents dismissing the entire result as metric circularity (p. 104, Fig. 40). Neither plot normalizes progress by total generation, rejected tasks, retries, GPU time, or human-valued capability. A finite rising cumulative count does not establish endless innovation.

The strongest reliability concern is **semantic success validation**. The authors abandoned preliminary VLM success detection as insufficiently accurate and instead use generated code (§3.6, p. 6; Appendix C, p. 16). Their 50-participant study reports 72.7% agreement with the detector (§5, p. 8; Appendix H, p. 102). This is agreement, not calibrated detector accuracy; a confusion matrix, task-level uncertainty, and human inter-rater reliability are not provided there.

The local paper supplies a concrete counterexample to treating executable code as faithful specification. “Construction Site Cleanup” requires picking up debris, placing it in the correct bins, and returning home (Appendix D, p. 18). Its printed `get_task_rewards` marks debris “picked” upon robot contact and permanently marks it “placed” upon contact with the corresponding receptacle; `get_success` uses those historical flags and the robot's return position (pp. 20–21, visually checked). It does not verify current containment, actual carrying, or the one-piece carrying constraint. This is a static discrepancy in a **simulated-learning** example, not an observed exploit by a trained policy or an estimate of its frequency. Nevertheless, separating reward and success functions cannot guarantee independent correctness when both inherit the same generated task interpretation. The success function also influences archive admission and future curricula, so it remains part of the larger optimization loop.

**Prioritized proposals — experiments, not changes performed.**

1. **P0: Define independently checked practice outcomes before generating curricula.** Build an isolated analysis artifact format with immutable task specification, environment/version hash, verifier version, initial/final state, outcome, and attempt provenance. For Navi-relevant practice, start with bounded synthetic evidence-retrieval or procedure-selection environments whose answers can be checked independently. Reuse the concepts at `finishAction` and `ProceduralMemory::observe`, while keeping goal-level success distinct from today's adapter postconditions (I05/Q36). This follows directly from the paper's reward/success separation and its demonstrated specification gap. Cost is fixture design and independent adjudication; generated executable code additionally needs an isolated runner with fixed dependencies and resource limits. **Evaluation:** challenge candidate verifiers with positive cases, near misses, temporary achievement followed by reversal, and reward-without-goal cases. Fail the gate if an adjudicated false success enters the learned-task archive; measure false negatives separately. Do not promote generated verifiers solely because their code executes.

2. **P1: Compare a success-and-failure archive against simpler generation.** Once P0 works, add an offline task catalog and proposal/critique pipeline, using immutable copied outcomes rather than production memory writes. Store task family, difficulty parameters, budget, failure reason, parent examples, and revised-task identity. Compare successful-only versus successful-plus-failed context; nearest-neighbor versus uniform retrieval; and generation-only versus generation plus a separate novelty check. Existing outcome IDs and lexical novelty checks are baseline ingredients (I08/Q36/Q42), not substitutes for the task catalog. Cost is model inference, adjudication, and multiple generation seeds. **Evaluation:** at fixed total model/execution budget, count independently verified, behaviorally distinct solved tasks and repetitive infeasible proposals. Failure means gains occur only in descriptions/embedding coverage, or disappear under a judge independent of the generator. Record compile failures, verifier failures, and insufficient training budget separately so invalid environments do not masquerade as capability limits.

3. **P2: Require retained transfer before connecting curricula to motivation.** In a disposable Navi-like runner, compare the same generated practice tasks with and without reusable validated procedures or retrieved lessons, using the boundaries in `ProceduralMemory::observe` and decision proposal assembly (`DecisionStateMachine::start:34`; I04/I08). This is speculative transfer of the paper's specialist-policy result to a different learner. Keep a frozen held-out suite and periodically replay earlier tasks with identical budgets. **Evaluation:** demand a positive improvement in held-out success per unit cost with uncertainty intervals excluding zero, while previous-task retention stays within a preregistered tolerance. Reject adoption if only generated-task pass counts improve. Until this succeeds, archive growth, curator acceptance, and daydream artifacts should not be used as evidence that `epistemic_novelty` satisfaction measures capability gain (Q09/Q36). The paper's approximately one hour on two RTX 6000 Ada GPUs plus 32 CPU cores per trained task illustrates why compute accounting matters (Appendix K, p. 106).

**Disagreements and verdict.** “Darwin completeness” concerns expressibility; it supplies no guarantee of tractable search, useful novelty, verifier correctness, or indefinite progress. The actual prompts constrain objects, robot affordances, imports, and task forms (Appendix L), and the authors explicitly acknowledge both simulator restrictions and absent generalist evaluation (§7, p. 10; Appendix O, p. 125). These constraints are reasonable engineering choices. They weaken any inference that arbitrary code generation alone removes the important limits on open-ended learning. For Navi, **experiment offline; defer production integration**. The decisive next step is a small independently verified practice archive that demonstrates retained capability gains under a fixed budget.
