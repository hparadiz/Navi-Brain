# EvolveMem: Self-Evolving Memory Architecture via AutoResearch for LLM Agents

**Authors/version:** Jiaqi Liu, Xinyu Ye, Peng Xia, Zeyu Zheng, Cihang Xie, Mingyu Ding, and Huaxiu Yao. 2026, arXiv:2605.13941v1, 13 May 2026; preprint. **Source:** [local PDF](../../../assets/papers/64-liu-et-al-2026-evolvemem.pdf). **Reviewer:** GPT-6 Astra. **Implementation evidence:** [shared master reference](IMPLEMENTATION.md), snapshot 2026-09-06, HEAD `ee1590009d6fd4c48035c63e15b3896a585757d7`; static source findings, not runtime validation.

**Assessment:** Experiment with failure-driven retrieval configuration search, but do not adopt this paper's claimed autonomous architecture discovery or its answer policies. The useful contribution is a concrete diagnostic loop around memory retrieval. Its strongest claims are weakened by evaluation-set reuse, explicit benchmark-specific prompting, and contradictions between the published algorithm and reported execution.

## Core idea and mechanism

EvolveMem treats retrieval configuration as an optimization target alongside memory contents (§3, pp. 3–6). Conversation windows become typed, independently interpretable memory units with embeddings, entities, timestamps, importance, and confidence. Extraction retries, smaller fallback chunks, and keyword coverage checks address missing source details. Consolidation merges near-duplicates, decays importance, and reinforces memories whose entities recur in queries (§3.1; Appendix A, pp. 13–14).

Three views independently retrieve candidates: BM25, embedding cosine similarity, and structured entity/location/person matches. SUM, normalized weighted sum, or reciprocal-rank fusion combines them; importance, recency, and entity reinforcement then modify ranking (Eq. 1, p. 5). Configurable dimensions include candidate counts, context size **in memory records**, fusion mode, answer style, and category overrides. Optional name-stripped retrieval, query decomposition, and answer verification add further paths. Changing fusion scales also changes the relative influence of additive memory-quality terms; this needs calibration rather than assuming interchangeable modes.

Each evolution round evaluates labeled questions, records predictions, references, scores, and retrieved sources, and asks an LLM to diagnose errors. A controller clamps proposed configurations, reverts large regressions, and perturbs configurations after stagnation. Missing-coverage diagnoses can trigger source re-extraction (§3.3; Algorithm 1). This is supervised, offline pipeline optimization using hosted models, not gradient learning or demonstrated lifelong adaptation under unlabeled deployment feedback. Its assumptions include reliable reference answers, reproducible evaluation, actionable diagnosis, and query categories that remain available outside the benchmark.

## Evidence and limitations

**Reported performance is encouraging but measures the whole pipeline.** LoCoMo covers 10 conversations and 1,986 QA pairs; GPT-4o F1 rises from 0.305 for a minimal BM25 baseline to 0.543, versus SimpleMem's 0.432. GPT-5.1 reaches 0.572 versus 0.418 (§4.1–4.2, Table 2, p. 7). These are respectively 11.1 and 15.4 percentage-point advantages over the strongest listed baseline. GPT-4o multi-hop F1, however, is 0.316 versus SimpleMem's 0.318: improvement is not uniform.

MemBench uses only 28 samples. Overall accuracy is 67.9% versus 57.1% for GPT-4o, and 71.4% versus 64.3% for GPT-5.1 (Table 3, p. 8): three and two additional correct answers, respectively. Robustness remains weaker than some baselines. No repeated-run variability, confidence intervals, or paired significance analysis is reported; LoCoMo questions also cluster within only ten conversations.

**The ablation supports engineering components more strongly than the headline evolution claim.** Removing extraction quality controls costs 23.22 F1 points; semantic retrieval costs 10.32; replacing diagnosis with random perturbations costs 9.63. Removing self-evolution costs only 2.03 points, leaving 52.27 F1 (Table 6, p. 9). The reported no-evolution row therefore retains most of the 23.8-point gain over the deliberately sparse baseline. Component-removal ablations rerun evolution, so they do not isolate each component at a common final configuration. The stated “joint” 7.77-point contribution of three discovered dimensions simply sums their individual removal effects; no simultaneous-removal row establishes that joint effect. Matched search budgets and the provenance of the no-evolution configuration are insufficiently specified.

**Generalization is not cleanly separated from optimization.** The diagnosis explicitly sees reference answers and repeatedly optimizes the evaluation questions (§3.3, p. 6; Eq. 14, p. 14). Appendix E mentions two held-out LoCoMo samples for default hyperparameters (p. 18), but does not explain their separation from the full ten-conversation result or identify an untouched final evaluation set for the evolutionary search. Label access is legitimate for training; these reporting gaps prevent interpreting the optimized score as clean held-out performance. Re-extracting memory after inspecting failures also changes the corpus, confounding configuration gains with improved extraction coverage.

Table 5 reports LoCoMo-to-MemBench transfer of 0.543, continued evolution reaching 0.792 on MemBench, and retained LoCoMo improving from 0.543 to 0.593 (p. 9). However, the untuned MemBench baseline is omitted, so 0.543 alone does not establish positive transfer relative to that baseline. Further evolution also spends additional optimization budget. Moreover, 54.3% and 79.2% cannot be rounded single-run exact-match accuracies over 28 equally weighted questions; an alternate denominator or averaging protocol is unexplained. Two benchmarks with these uncertainties do not establish “universal retrieval principles.”

**Autonomous dimension discovery is not demonstrated by the published interface.** Section 3.3 claims new parameters emerge without rubric modification. Yet Appendix F.6 explicitly tells diagnosis to enable entity-swap and answer verification, favors LoCoMo prompt flags, lists disabled features, and requires parameter fields to match `RetrievalConfig` exactly (pp. 21–22). Table 7 already enumerates the supposedly discovered capabilities. The paper does not document executable module generation, schema extension, or validation that would turn an unknown field into working retrieval behavior. This supports informed selection of available mechanisms; historical invention would require additional code/version evidence. The final prompt cannot substantiate benchmark-independent discovery.

**The stopping rule contradicts the reported trajectory.** Algorithm 1, lines 17–18, and Eq. 16 stop whenever the latest improvement is below 0.005, including a regression (pp. 6, 14). Table 4's R2 drops from 35.8% to 34.8%, which would terminate execution before R3–R7. The first near-zero change also prevents reaching two consecutive stagnating rounds for exploration. A later R5 decline likewise conflicts with continuation. Thus the printed controller cannot generate the described trajectory as written. Separately, reverting only configuration does not restore a jointly evolving memory store; Algorithm 1 saves the best configuration without a corresponding best-store snapshot.

Reproducibility details also need reconciliation: Appendix E says answer generation uses GPT-4o for all categories despite two-backbone results; Appendix D.3 gives 25–35 minutes for seven rounds while describing 15–20 minutes of QA evaluation per round (p. 17). These may reflect different runs or execution assumptions, but the local version does not resolve them. Reported 15 ms retrieval covers about 900 memories; it establishes neither large-store scaling nor full answer latency, especially with extra model calls.

**Answer correctness and benchmark score can diverge.** The LoCoMo prompts forbid “unknown,” instruct substantive answers despite swapped names, and sometimes demand plausible guesses. The verifier replaces abstention with the likeliest answer (Appendix F.3–F.5, pp. 19–21). The case study explicitly tunes an “and” connector to recover token F1 (Table 8, p. 16). These policies can improve lexical scoring while increasing unsupported assertions or misattributing one person's experience to another. Recency is also not a general solution to historical temporal questions. I would reject these policies as Navi defaults. Near-duplicate merging by 80% token overlap can similarly erase consequential negations, dates, or changed project decisions.

## Mapping to Navi-Brain

**Already implemented:** Navi has persistent typed memory, provenance, consolidation, and online token/association learning. [I02](IMPLEMENTATION.md#i02--resident-token-memory-retrieval-persistence-and-learning) verifies `memories/src/tokmem.c::encode_greedy`, `crystallize_online`, and `query_memories`; [I08](IMPLEMENTATION.md#i08--consolidation-sleep-and-procedural-learning) verifies `src/Core/ExecutiveCore.php::enqueueConsolidation:3159` and `integrateConsolidation:5020`, including source hashes and grounding checks. These are reusable foundations, not EvolveMem's embedding/BM25/metadata fusion architecture.

**A consequential ranking difference:** I02 and **Q57D** verify that `tokmem.c::scored_memory_better:5359` ranks lexicographically by ACTIVATE span coverage, access count, and update time/unique ID. The unique-ID tie-break prevents later direct/total score terms from ordering distinct valid records. Associations still determine candidate reachability, and direct score separately gates ACTIVATE packing. `src/Storage/TokenMemoryDaemon.php::sortRecallByKeywordCoverage:360` reranks only native top-k. Consequently, blindly adding “fusion weights” downstream cannot rescue excluded relevant memories; repeated access can promote an old active record without measuring usefulness.

**Partially available:** `src/Core/DecisionStateMachine.php::start:134–191` performs one initial limit-eight search; retrieved IDs and subsequent action evidence provide partial diagnostic linkage. **Q03/Q58** establish that this is neither an adaptive within-cycle query loop nor a labeled replay evaluator; `DecisionStateMachine::compare:682` aggregates stored outcomes without executing held-out tasks. **QMEM** establishes that ranking without counting candidate reads still learns query links and token usage, so replay through nominally neutral ranking can contaminate later comparisons.

**Absent in the master's bounded search:** the paper-specific **Q64** follow-up finds no production retrieval-configuration proposal → labeled replay → promotion/revert controller, nor an exposed native ranking/fusion-weight configuration consumer. Native cue weights are compile-time constants; `TOKMEM_RANK_INTERVAL_MS` controls maintenance cadence, not the ranking objective. Existing adjustable boundaries include recall limits, filters, cue text, and ACTIVATE token budget. **Q59** separately establishes that `src/Core/PublicReflection.php::runOnce:23` and `review:100` produce/review proposals rather than execute an evaluation/promotion loop. An EvolveMem-style controller would add machinery; external research experiments and deployed behavior remain outside this static finding.

## Prioritized recommendations

1. **P0 — Establish reproducible failure attribution before tuning.** Propose an isolated evaluator around the `TokenMemoryDaemon` retrieval boundary and `DecisionStateMachine::start`, reusing source/cycle IDs. Record gold evidence, whether it survived extraction, candidate membership/rank, packed context, prediction, and configuration. Freeze the complete relevant token-memory state—not only text—and replay identical query orders from identical initial copies because retrieval itself learns (**I02/QMEM**). Separate tuning conversations from untouched evaluation conversations and include correction, historical-time, paraphrase, and unanswerable cases. Dependencies are independently labeled fixtures and faithful state reconstruction; this is proposed research infrastructure, not work performed here. **Failure criterion:** repeated fixed-policy replays must reproduce retrieval IDs/order; otherwise optimizer comparisons are invalid. Report source recall separately from answer correctness so extraction gaps cannot masquerade as ranking failures.

2. **P1 — Compare explicit ranking alternatives before adding an LLM optimizer.** At `tokmem.c::scored_memory_better` and `append_activation_context:4922`, experimentally compare current ordering with relevance-before-access and bounded/decayed-access variants; keep corpus, candidate reachability, context-token budget, and answer policy fixed. Include PHP reranking and ACTIVATE packing as separate conditions (**I02/Q57D**). This is a speculative transfer of EvolveMem's configurable-retrieval idea, not its algorithm. Native ranker parameterization and instrumentation are dependencies. **Promotion criterion:** on untouched conversation groups, require a positive paired improvement in gold-evidence recall and grounded-answer accuracy, with no increase in superseded-record eligibility and no more than a predeclared 10% p95 retrieval-latency penalty. Failure or a gain confined to frequent repeated cues rejects the change. Preserve existing active-status filtering (**Q57S**).

3. **P2 — Trial bounded diagnosis only after a useful action space exists.** Build a separate offline controller accepting existing typed parameters; keep schema/code generation outside this experiment. Version the configuration, extraction/store state, prompts, evaluator, and model together. Fix stopping semantics so a rejected trial actually restores state and exploration receives its declared budget. Compare diagnosis with an informed fixed configuration and equal-cost random search, separately enabling re-extraction and answer verification. Dependencies include P0–P1, model-call accounting, and enough independent conversations to resolve modest gains. **Success criterion:** diagnosis must improve untouched grounded-answer accuracy over both controls, with a paired 95% confidence interval for each gain entirely above zero using conversation-level resampling, within a fixed total search budget, while unsupported-answer rate rises by no more than one percentage point. Otherwise retain the fixed policy. Keep abstention valid and entity identity binding; the paper supplies no justification for relaxing either.

## Verdict and coverage

**Experiment, with substantial evidential reservations.** The highest-value next step is reproducible source-recall diagnosis at Navi's actual native ranking/packing boundary. EvolveMem motivates that work, but does not justify autonomous production retrieval evolution or replacing provenance safeguards with benchmark-oriented guessing.
