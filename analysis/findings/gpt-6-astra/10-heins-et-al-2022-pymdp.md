# pymdp: A Python library for active inference in discrete state spaces

Conor Heins, Beren Millidge, Daphne Demekas, Brennan Klein, Karl Friston, Iain D. Couzin, and Alexander Tschantz (2022). *Journal of Open Source Software* 7(73), 4098; published 4 May 2022; DOI: [10.21105/joss.04098](https://doi.org/10.21105/joss.04098). Reviewed version: the local six-page published JOSS article, [source PDF](../../../assets/papers/10-heins-et-al-2022-pymdp.pdf). Reviewer: **GPT-6 Astra**. Implementation evidence: [shared implementation reference](IMPLEMENTATION.md), snapshot 2026-09-06, git HEAD `ee1590009d6fd4c48035c63e15b3896a585757d7`.

**Verdict: experiment in a small offline domain; defer production adoption.** The useful contribution is a modular implementation substrate for explicitly specified discrete generative models. This paper supplies neither evidence that active inference outperforms Navi's existing decision rules nor a worked derivation sufficient to implement its inference algorithms. The most consequential next step is to determine whether a small, calibrated model improves the choice of diagnostic observations over simpler policies using the same information.

**Source coverage and evidential status.** I read all six pages, including the references, and visually checked PDF page 2's model notation and surrounding explanation. PDF and printed page numbers coincide. The substantive software description occupies pp. 1–3; funding and acknowledgements extend into p. 4, and references occupy pp. 4–6. There are no appendices, benchmark tables, experimental figures, or worked simulations in this local article. The companion arXiv preprint is explicitly referred to for mathematics on p. 2 and cited as version 1 on p. 5; its contents are not evidence reviewed here. No code execution, tests, or experiments were performed. Implementation statements below come exclusively from the shared master's static inspection.

The paper addresses a concrete software problem. Active-inference researchers had relied heavily on MATLAB's DEM toolbox, especially `spm_MDP_VB_X.m`. License access and concentrated, application-specific routines obstructed reuse. The authors present Python implementations with separable inference and policy-selection functionality, a high-level `Agent`, and an `Env` interface following Gym's observation/action exchange pattern (pp. 1–2, “Statement of Need” and “Summary”; p. 3, “Related software packages”). This is an accessibility and software-composition contribution, rather than a new experimentally demonstrated cognitive capacity.

The computational substrate is a partially observable Markov decision process. The paper writes the generative model as a joint distribution over observations, hidden states, controls, and hyperparameters, **P(o, s, u, φ)**, factorized into categorical and Dirichlet distributions (p. 2, “Summary”). Hidden states evolve probabilistically under actions, and observations provide indirect evidence about those states. An agent therefore needs both inference about its present situation and selection of future controls associated with desired outcomes (p. 2, “Introduction”). Categorical variables make finite alternatives explicit; Dirichlet distributions provide the stated probabilistic parameterization of the model's priors. The article does not give parameter-learning update equations or specify the complete time-indexed factorization.

The design separates model specification, inference routines, and environment interaction. Users can call `Agent` methods in an application-specific order, select lower-level implementation options, or subclass it with a custom `step()` combining selected components (p. 3, “Usage”). Marginal-message passing is named as one selectable state-estimation algorithm (p. 3, “Related software packages”), but is not derived or evaluated. This modularity is valuable for asking whether a result comes from better state estimation, a different policy rule, or parameter learning. It also places responsibility on the integrator to preserve a coherent observation–inference–action sequence; arbitrary method composition is not a correctness guarantee.

Several assumptions determine transfer. The chosen finite state representation must preserve the distinctions needed for the task. The Markov description requires that the current modeled state, together with the action, adequately predicts subsequent states; persistent unmodeled history can invalidate that approximation. Observation likelihoods must distinguish informative evidence from noise. Desired outcomes must be specified operationally. These are modeling requirements implied by the POMDP formulation, not capabilities automatically supplied by importing the library. The paper's “few lines of code” claim concerns constructing and connecting an agent after supplying a generative model (p. 2); it does not measure the difficulty of discovering a useful model of an open-ended software environment.

**What the evidence establishes.** The article describes the package as “robust, tested, and modular” (p. 2). It provides neither numerical correctness comparisons against DEM nor test coverage, runtime measurements, sample-efficiency results, or user studies. Its comparisons with DEM and ForneyLab concern language access, organization, abstraction levels, and intended use (p. 3). They do not establish superiority in planning performance or inference accuracy. The broad applications cited on p. 1 are motivation from other work, not experiments conducted in this paper. Likewise, the claim to be the first open-source package for this particular purpose is the authors' historical claim, not independently verified here.

The evidential limit matters especially for expected free energy. This article does not display that objective, its decompositions, a policy-posterior update, or an exploration benchmark. Discussion below of information-seeking policy experiments is **proposed engineering synthesis**, motivated by the package's advertised active-inference support. It must not be read as a theorem or measured result from this PDF. A chosen release and its algorithm documentation would have to establish the exact implemented objective and options before numerical reproduction.

**Mapping to Navi-Brain.** The strongest architectural fit is a bounded estimator/planner that proposes diagnostic actions inside the existing executive. The shared reference supports these distinctions:

There is also genuine hypothesis inference in `OtherModel` (I09), so “Navi has no probabilistic beliefs” would be false. The narrower missing connection is an explicit predictive model used to compare the consequences and information value of the diagnostic actions under consideration. Meanwhile, token-memory association learning remains its own mechanism (I02); renaming learned token links as POMDP transition probabilities would erase their actual semantics.

Integration should target terminal-candidate evaluation, not assume `ActionSelector::choose` is a universal executor. I04/Q08 establish that its inspected direct use gates unprompted speech; selecting another action there does not itself dispatch every alternative. Q03 also establishes that the decision cycle has initial retrieval followed by a single proposal, without an adaptive within-cycle retrieval loop. A multi-step policy would therefore require an explicit mechanism for carrying beliefs forward and incorporating new observations. A list of future actions in model-generated prose would not implement that mechanism.

**Prioritized recommendations.** All evaluations below are proposals, not performed work.

1. **P0 — Specify one finite diagnostic model before introducing a dependency.** Build a future offline model contract corresponding to a bounded observation choice: for example, distinguish normal operation, a transient fault, and a stale sensor in a simulator. Specify observation likelihoods, action-dependent transitions, initial beliefs, outcome preferences, observation costs, and the treatment of missing data. Keep the initial model small enough for exact enumeration. The eventual data boundaries are `ForwardModel::observe` for readings and `ProceduralMemory::inspectCandidate` for available actions; an actual mapping to installed `machine.look` sources remains unverified. Pin the pymdp release, inference routine, tolerances, and random seeds. Validate filtering against an independently computed finite-state Bayesian reference; approximate inference must have a declared error tolerance, rather than being assumed exact. Evaluate calibration on held-out simulated episodes and perturbed likelihoods. **Failure:** invalid normalization, reference discrepancies beyond the chosen tolerance, or no calibration benefit over a simple persistence/base-rate model. The principal cost is specifying and validating the state abstraction, not writing the API calls.

2. **P1 — Isolate the value of active observation selection.** Using the same model, candidate actions, preferences, and budgets, compare the selected pymdp planning configuration with a belief-aware greedy expected-cost policy, a one-step information-gain heuristic, and an exact small-POMDP solution where tractable. Include Navi's current candidate scorer only where the simulator supplies its genuine input fields; mark any adaptation explicitly. Design paired cases where observations resolve uncertainty and where equally surprising observations are irreducible noise. Vary observation costs and horizon; ablate the planner's epistemic term only if the pinned implementation exposes and documents it. Measure diagnostic error, total observation cost, steps to a correct decision, and isolated planning latency. Predeclare a minimum useful improvement and confidence interval. **Failure:** gains disappear against the equally informed greedy baseline, noisy channels attract repeated unhelpful sampling, or the planner exceeds its resource budget. This determines whether the benefit comes from having a belief state at all or from the more elaborate policy objective. No result here would establish a general advantage across Navi's tasks.

3. **P2 — Consider executive integration only after P0/P1 succeed.** Prototype a proposal-only planner boundary before selection in `DecisionStateMachine::integrate`, retaining `ProceduralMemory`'s installed-adapter validation and recording model version, observation IDs, belief state, candidate set, objective components, horizon, and elapsed time. Start with shadow decisions. Recompute or reject proposals when relevant observations change: Q02 verifies that the present integrator does not compare its saved workspace checksum with current workspace state. Keep outcome preferences separate from hard admissibility rules; the paper supplies no authorization mechanism, and I05/Q23 do not establish a universal interrupt veto. **Failure:** stale evidence changes an accepted decision without detection, invalid actions reach dispatch, planner timeouts lack a bounded fallback, or replay cannot explain the ranking. Python packaging, serialization, correlated timing, and belief persistence are additional costs; none is justified merely by thematic alignment with active inference.

The principal disagreement with an ambitious adoption reading is that modular active-inference software does not solve Navi's state-discovery problem. Finite models can be excellent for a narrow diagnostic task while failing on open-ended intentions, language, and changing tool inventories. Naively enumerating action sequences also grows exponentially with horizon; this is a general planning concern, not a measured limitation of this particular release. Strong preference settings or incorrect likelihoods can make a model confidently pursue the wrong observations. A successful simulator demonstration would establish a mechanism under its assumptions, with real-data transfer still requiring evaluation.

The published article warrants treating pymdp as an experimental reference implementation. It does not warrant replacing Navi's memory system, executive lifecycle, or action-authority boundaries, and offers no evidence about consciousness. The installed package state, exact candidate release behavior, and suitable live observation schemas remain unverified; none is required for the present offline-experiment verdict. The immediate deliverable should be a small generative-model specification and a fair comparison design, followed by adoption only if the more elaborate planner earns its cost.
