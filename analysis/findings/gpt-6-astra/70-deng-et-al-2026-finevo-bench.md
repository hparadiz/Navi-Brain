# FinEvo-Bench: A Longitudinal Benchmark for Self-Evolving Agents in Professional Financial Workflows

## Core contribution and mechanism

FinEvo-Bench contributes an evaluation protocol and financial task collection, rather than a new learning algorithm. Its useful distinction is between **absolute capability after experience** and **improvement attributable to retaining experience**. These can rank agents differently. Its operational “self-evolution” means updating external memories or skills after feedback and reusing them on subsequent tasks; model parameters remain fixed (§§1, 3–4, pp. 1–4).

The collection contains 120 tasks, six substantively different cases in each of 20 scenes across six financial domains, with 775 input files. Institution-provided professional procedures define operations and constraints; screened institutional/public cases supply facts. Two experts develop and review each shared scene rubric. Tasks demand open-ended artifacts, including calculations, evidence reconciliation, recommendations, and appropriate professional boundaries. Sharing a workflow while changing conclusions is a sensible transfer challenge: remembering an analysis procedure should help, while remembering the previous credit decision may hurt (Table 11, p. 11).

Each scaffold processes three independently shuffled, globally interleaved task streams. A task is executed, judged, and then reflected upon in its original conversation; the next task starts a new session with persistent experience retained. Paired controls reset state before each task while matching task order, backbone, decoding, and scoring. The primary estimand is the mean paired difference, evolving score minus reset score; compliance improvement reverses that subtraction. Early/late gains average within-scene occurrence ranks 1–3 and 4–6 (§4.1, equations 2–6, p. 4).

All four evaluated scaffolds use Qwen3.7-Max, including those named Claude Code and Codex. The independent scoring scaffold uses Claude Opus 4.6. Thus these are scaffold comparisons under one execution model, not comparisons between their usual model families. Letta injects every core memory block into every call; the other scaffolds selectively load stored experience.

## Results and strength of evidence

Table 3 (p. 6) reports means over the three streams:

| Scaffold | Evolved score /100 | Paired score gain | Compliance issues/task | Agent tokens/task |
|---|---:|---:|---:|---:|
| Claude Code | 89.47 | +17.89 | 0.11 | 765,000 |
| Codex | 91.17 | +19.37 | 0.11 | 687,500 |
| Letta | 91.65 | +17.82 | 0.09 | 504,300 |
| GenericAgent | 83.34 | +9.33 | 0.34 | 217,800 |

Token totals include execution and reflection but exclude judging. Compliance reductions range from 0.12 to 0.44 issues/task. Late gains exceed early gains by 6.10–8.70 points, with that direction present in all three permutations. This supports a retained-experience benefit within these recurring workflows, subject to the protocol uncertainty below.

The strongest carrier comparison is within Claude Code (Table 5, p. 6): skill-only reaches 93.71, memory-only 90.42, and their unrestricted combination 89.47. Skill-only also has fewer compliance issues, 0.05/task. More storage mechanisms did not produce better performance. However, an initial fixed expert skill already reaches 86.67 against the reset baseline's 71.58: a **15.09-point improvement**, calculated from the table, leaving only 2.80 points between that baseline and unrestricted evolution. Reflection consumes 601,900 tokens/task in the latter. A well-authored initial procedure is therefore an essential practical comparator.

Rubric feedback outperforms complete reference-answer feedback by 3.95–7.93 points across scaffolds (Table 6). Appendix C supplies a concrete update trace: an 88/100 report's six deductions become arithmetic, missing-evidence, and quantitative-attribution checks in both memory and skill instructions (pp. 17–22). This demonstrates persistent representation changes. It does not independently demonstrate that those particular edits caused a later task's improvement. The “skill” excerpts are instructions and formulas interpreted by an agent, not evidence of compiled, mechanically enforced financial routines.

The judge validation is unusually useful: one financial expert independently scores 120 outputs from one complete main-experiment run, yielding absolute-agreement ICC(A,1)=0.95, 95% CI [0.93, 0.97], mean absolute disagreement 1.6 points, maximum 5 (§4.2, p. 5). This supports numerical scoring fidelity on that sample; it does not validate every scaffold, individual compliance flag, or later adaptive distribution.

## Material limitations and disagreements

**Feedback isolation is internally inconsistent.** Section 4.1 says agents never receive the judge's full item-level record and receive only summarized problems/reasons (p. 4). Appendix B instead instructs the judge to check every item and write the complete scoring result to `judge.md`, then places that same file into the agent's reflection workspace (Algorithm B.1, p. 15; Figures 6–7, p. 16). No filtering step is documented. I visually verified these PDF pages. Appendix C also preserves criterion-linked two-point deductions in the learned skill (Table 28, p. 21). Retaining deductions alone does not prove that the full rubric was exposed, but the appendix does not substantiate the main text's narrower visibility claim. Actual released feedback and harness behavior remain unverified. Treat the result as feedback-assisted workflow adaptation with uncertain evaluation-detail exposure, rather than established isolation from the scoring specification.

**Repeated rubrics permit evaluator-specific learning.** Learning professional requirements is the intended intervention, so repeated criteria are not automatically contamination. Nevertheless, one fixed judge both generates feedback and scores subsequent artifacts against the same scene rubric. Held-out cases test new facts; they do not test unfamiliar professional standards or evaluator independence. The largest normalized improvement is report quality for every scaffold (Figure 4, p. 7), making separate arithmetic, factuality, and presentation outcomes particularly important.

**Precision is weaker than the displayed decimals.** No confidence intervals or dispersion accompany scaffold differences, carrier effects, or feedback effects. Tasks share scenes and evolving histories, so 360 task observations are not 360 independent learning runs. Letta's 0.48-point absolute-score lead over Codex is descriptive. The judge agreement interval is not an uncertainty estimate for any treatment effect.

**Activation is not a causal utilization measure.** Selectively activated tasks score 8.31–9.06 points higher than non-activated tasks (Table 4). Retrieval is chosen rather than randomized; task difficulty, stream position, and prior learning can explain the gap. Comparing non-activated subsets against the overall reset average also mismatches task distributions. Letta's 120/120 activation is an interface property, correctly acknowledged by the authors, not evidence of universally useful retrieval.

**Longitudinal exposure is short and confounded with global progress.** A scene has only six occurrences; later within-scene ranks also occur later globally. The authors acknowledge that accumulation can include broader experience. The five-scene, one-order interference diagnostic finds mixed score changes of −1.00 to +1.63 and only 0.01–0.05 additional compliance issues under isolation (Table 7, p. 7). This is insufficient to establish robust cross-domain transfer, forgetting resistance, or indefinite memory scalability.

Finally, “compliance issues” are rubric triggers in submitted artifacts. The example includes missing scope statements and critical analysis omissions alongside fabricated data and prohibited assurances (Table 16, p. 13). Their unweighted count is not expected financial harm, regulatory certification, or successful real-world lending. Report quality, numerical correctness, and operational safety require distinct interpretations.

## Prioritized recommendations and falsifiable evaluations

**P0 — Adopt the paired evaluation design with an explicit feedback boundary; defer production architecture changes.** Build a separate research harness around disposable executive/token-store instances, using Q58's `DecisionStateMachine::compare` only as trace input. Start with six engineering workflow families and six different cases each, interleaved under at least three permutations. Keep model, tools, starting knowledge, task order, and budget limits identical across reset, frozen learned-state, and continuing-update conditions. Reset transient task context between cases. Freeze all declared persistent learning state, including token associations/access statistics, rather than only semantic text; I02/Q64 establish query-side mutations and that checkpoints are not restore images.

Archive full judge records separately from the explicitly defined defect feedback shown to reflection. Keep final artifacts immutable before scoring. Include unseen cases and delayed old-case probes scored without supplying their feedback to training. Report paired quality gain, severe-error incidence, arithmetic/factual accuracy, retention, tokens, and latency, with uncertainty respecting scenes and complete stream histories. This needs task authoring, isolated state capture, and independently checked acceptance criteria. **Failure criterion:** any evaluator-only material reaching execution/reflection invalidates the isolation claim; no positive held-out gain with an interval excluding zero fails to establish improvement. Any new severe authority or fabrication failure blocks adoption despite a higher mean score. These are proposed gates, not reported results.

**P1 — Compare fixed expert guidance against feedback-derived, applicability-limited procedures.** Appendix C motivates converting a specific failure into a check that acts before delivery. At the existing consolidation/proposal boundary (`ExecutiveCore::integrateConsolidation`) and decision prompt construction (`DecisionStateMachine::start:210`), experimentally represent each lesson as trigger, required inputs, check, missing-input behavior, and supporting feedback IDs. Preserve the existing grounding guards; evaluator feedback is evidence about a past artifact, not universal authority. Keep case-specific values and decisions out of generalized instructions.

Compare fixed expert checklist, evolving semantic guidance, evolving ordered checklist, and combined guidance with equal exposure and token budgets. Call the ordered checklist a prompt procedure unless its operations are actually expressible and verified through installed adapters; do not expand execution authority merely to mimic the paper's terminology. Include cases with reversed conclusions and missing inputs to detect rote copying or impossible requirements. Costs are independent defect labels, candidate review, and reflection/context tokens. **Failure criterion:** reject dynamic updates unless they improve held-out quality over the fixed checklist at the declared budget without increasing unsupported assertions; reject the combination unless its marginal benefit justifies its extra cost.

**P2 — Test retrieval benefit by intervention before increasing memory exposure.** The skill/memory combination's underperformance suggests a routing hypothesis, not a mandate for always-on memory. In isolated copies of identical pre-task states, randomly expose or mask the same retained guidance while preserving other inputs. Use `DecisionStateMachine::start` before both supporting-evidence publication at line 180 and prompt construction at line 210; Q66 warns that masking only the retrieval block allows the first memory to reenter through working context. Audit other context consumers for the same leakage.

Record candidate IDs, actual context exposure, task outcomes, and cost separately from access counts. Include unrelated intervening tasks to measure distraction. This requires context-exposure instrumentation and clean cloned states because retrieval itself can learn (I02/Q64). **Failure criterion:** if randomized exposure produces no supported benefit, or increases cross-case contamination, activation-rate gains do not justify broader loading. This causal extension is my proposed synthesis; FinEvo-Bench did not perform it.

## Verdict and coverage

**Adopt the evaluation distinction; experiment with feedback-derived procedures; defer a memory-architecture preference.** The consequential next step is a clean paired longitudinal evaluator with a fixed expert-checklist baseline. Navi already has persistence and bounded learning; the missing evidence is whether those mechanisms improve independently judged later work enough to justify their costs.
