# 05 — Intention Is Choice with Commitment

- **Paper**: Intention Is Choice with Commitment
- **Source**: P.R. Cohen and H.J. Levesque, Noûs, 1990 (submitted 1987, revised 1988)
- **Local file**: assets/papers/05-cohen-levesque-1990-intention-choice-commitment.pdf

## Core idea

Cohen and Levesque give intention a crisp functional definition: an intention is a **persistent goal** (P-GOAL), not a one-shot desire or a plan-data structure. An agent holds a P-GOAL until it believes the goal is achieved, believes it is unachievable, or believes the background conditions that justified it no longer hold.

They split intention into two operators. `INTEND1` covers committed action sequences, including conditionals and while-loops whose unfolding need not be known up front — so an agent can intend to chop a tree down without knowing which swing does it, intending only to repeat the chopping event until the tree is down. `INTEND2` covers committed world-states where the agent has no plan yet, only a commitment to do *something* that brings the state about while believing it will; this handles cases like "intend to become rich" where the agent cannot yet name the action sequence.

The formalism then proves the commonsense properties that philosophers expect of intention: intentions pose problems for later reasoning, provide a "screen of admissibility" against adopting conflicting commitments, survive a single failure (the agent keeps the intention if it does not believe the goal is now impossible), and do not require intending all foreseen side-effects (the dentist patient who expects pain does not intend the pain).

The paper also handles the "Little Nell" problem — an agent should not drop a goal because it believes it *will* succeed, only because it believes success is already achieved — by defining P-GOAL so that the goal must hold *later* and the agent must not believe it holds *now*.

Section 8's "relativized persistent goal" (`P-R-GOAL x p q`) makes the backing conditions `q` explicit, so an intention can be dropped when the belief or supergoal that justified it is retracted. The architectural punchline, stated plainly in Section 9, is that this is a *specification* for agent design, not a logic for the agent to reason with: encode a dependency network among beliefs, goals, and commitments, and let the agent be "committed by architecture" because that network is wired into the release conditions. The paper closes with social commitments emerging from interlocking relativized goals between agents, pointing toward joint intention without requiring any mystical group mind.

## Relevance to Navi-Brain

This is the theoretical backbone of Navi-Brain's entire intention substrate, already cited in `docs/literature-synthesis.md` (Section 3, "Persistent intentions"). The paper's "relativized persistent goal" (`P-R-GOAL x p q`) maps directly onto what `src/Model/Intention.php` is trying to be, but Navi-Brain currently implements only the flat, non-relativized version — there is no field that records *what the intention is held relative to*, and no resolver that releases it when that backing condition drops.

The paper explains *why* the `dependencies`, `release_condition`, and `parent_id` fields that already exist on `Intention.php` are not decorative: they are the dependency network that prevents fanatical persistence. It also gives formal teeth to the safety invariant that user authority outranks persisted intentions — a `P-R-GOAL` with backing condition `q = (GOAL user p)` is cleanly released when the user drops that goal, which is exactly the corrigibility property Navi-Brain wants.

The screen-of-admissibility result (`Theorem 7.1`: `INTEND x b` plus belief that `a` defeats `b` entails not-`INTEND x a;b`) is directly usable as a conflict check before intention adoption. And the paper's warning against dropping goals on predicted success rather than achieved success is a precise statement of why Navi-Brain's `release_condition` must test for *believed achievement*, not *believed future achievement*. The paper's handling of `INTEND2` also clarifies what Navi-Brain's `Need.php` model is missing: needs are pressures, but they should be expressible as commitments that pose problems for later reasoning.

## Cross-reference to the existing system

**Already present.** `src/Model/Intention.php` records `reason`, `authority` (user/developer/system/agent), `next_action`, `success_condition`, `release_condition`, `dependencies`, `parent_id`, and a `status` enum covering active/blocked/completed/released. This is the paper's "chosen goal + supporting reasons + release conditions" checklist, almost line for line. The `dependencies` column is the raw material for the dependency network the paper demands. The `release_condition` field already lets an intention be dropped without explicit completion.

`src/Model/CognitiveThread.php` carries `support_refs`, `current_belief`, `uncertainty`, `desired_outcome`, `progress`, and `stagnation_count`, which is where the backing beliefs and evidence-of-progress live for the cognitive-threads design. The heartbeat rhythms in `src/Model/Rhythm.php` (`pulse_30s`, `reflect_5m`, `consolidate_hourly`, `sleep_daily`) and the single-flight work item in `src/Model/WorkItem.php` provide the ticking clock the paper's temporal logic needs in practice, even though Navi-Brain uses wall-clock leases and monotonic fencing tokens rather than modal operators. `src/Model/CycleRun.php` tracks run history so the system can detect and drop expired work rather than replaying a catch-up storm — consistent with the paper's insistence that agents should not be fanatical.

**Partially present.** The paper's relativization is not implemented. An intention's `dependencies` array is stored in `Intention.php` (line 55) but there is no code path in `src/Core/ExecutiveCore.php` that inspects the *live truth* of those dependencies to decide whether to auto-release the intention. The paper wants an intention held "relative to" a belief or supergoal to be dropped the moment that belief is retracted or that supergoal is abandoned — today Navi-Brain would need an external process to notice and release it.

The screen-of-admissibility theorem is documented nowhere and not enforced at `intention:add` time; the `intention:add` path trusts the caller not to stack conflicting commitments. `CognitiveThread.php` has a `parent_intention_id` (line 34) and `support_refs` (line 55), which is the seed of the paper's inter-intention dependency web, but threads are "designed but not yet wired into a running loop" per `_SYSTEM.md`, so the dependency web is dormant. The `dependencies` column on `Intention.php` is a serialized array with no resolver attached.

**Absent / open design.** Interpersonal and interlocking commitments (`Section 8.2`). The paper's two-agent pattern — `(P-R-GOAL x p (GOAL y p))` and `(P-R-GOAL y p (GOAL x p))` — is a primitive joint-intention capability Navi-Brain does not model at all. So is the paper's claim that adoption of `P-R-GOAL` is the right way to handle a speech-act request: the hearer adopts a commitment relative to the speaker's goal, and is released when the speaker withdraws it. This is a clean formal handle on the "user authority outranks persisted intentions" invariant, but it is currently undocumented and unimplemented.

The paper's `INTEND2` — commitment to a world-state without a plan — also has no direct counterpart; Navi-Brain's intentions all assume a known `next_action` (line 46 of `Intention.php` is not null). `src/Model/Need.php` describes states the agent wants to bring about, but needs are *pressures*, not *commitments* — they do not carry the rational-release semantics the paper requires.

## Concrete implications for implementation

1. **Wire dependency-aware release into the reflection pass.** In `src/Core/ExecutiveCore.php`, during `reflect_5m` (or a lighter pass in `mind:tick`), iterate active intentions, evaluate each one's `dependencies` and `release_condition` against current beliefs and active supergoals, and move released intentions to `released` with a `closure_note` explaining why. The fields exist; the missing piece is the resolver loop that queries live state. This is the cheapest way to stop intentions from persisting fanatically. It should use the same single-flight fencing token pattern as `WorkItem.php` to avoid double-processing.

2. **Enforce screen-of-admissibility at `intention:add`.** Before inserting a new intention, query existing active intentions and check whether the new commitment's success condition conflicts with any of them under the agent's current beliefs. Reject or flag the conflict. This is a direct implementation of Theorem 7.1 and guards against silently stacking commitments the agent itself believes are incompatible. It could live as a pre-insert check in `ExecutiveCore.php`'s intention-add path.

3. **Make relativization explicit in the schema.** Add an optional backing-condition reference to `Intention.php` — either a `relates_to_type` / `relates_to_id` pair (pointing to another intention, a self-model fact in `SelfModelFact.php`, or an event in `Event.php`) or a structured `backing_condition` column that records the `q` in `P-R-GOAL x p q`. This makes the paper's "relative to" relation queryable and gives the release resolver something to check against. Document the semantics in `docs/literature-synthesis.md` alongside the existing Cohen-Levesque entry in Section 3.

4. **Document the speech-act commitment pattern.** Add a note to `docs/ongoing-cognition.md` or a new file under `docs/experiments/` describing how a user request maps to `P-R-GOAL addressee a (GOAL user a)` and how release happens on user withdrawal. This is the cleanest formal expression of corrigibility-by-commitment that the codebase has, and it would anchor future worker/curator designs and the human-to-agent authority model.

5. **Use `INTEND2`-style commitment for open-ended needs.** Some entries in `src/Model/Need.php` are states the agent is committed to bringing about without a fixed action sequence (e.g. continuity, model fidelity, replica health). Recording these as intentions with a clear `success_condition` and a null or unspecified `next_action` would let the reflection pass plan the action later, matching the paper's "commitment poses a problem for later reasoning" role. This would also unify the needs and intentions models under a single commitment semantics.

6. **Add a conflict-check experiment.** Under `docs/experiments/`, design an experiment that stacks two intentions with contradictory success conditions and verifies the screen-of-admissibility check rejects the second. This would validate the paper's Theorem 7.1 against the actual codebase and catch regressions.

7. **Persist belief-intention links in the self-model.** The paper's P-GOAL depends on the agent's beliefs being queryable at release-check time. Navi-Brain's `src/Model/SelfModelFact.php` tracks capabilities and permissions but not the live belief state backing each intention. Extending the self-model (or a dedicated intention-belief edge table) to record which beliefs justify which intentions would make the dependency-release resolver fully data-driven.

8. **Respect the "not nondeterministic" constraint in action selection.** Proposition 5.4 implies that an agent believing it is about to do a disjunction must believe it is about to do one specific branch, or believe in a common initial step. For Navi-Brain, this means the `next_action` field should always be a concrete primitive, not a disjunction — the reflection pass must resolve any conditional or disjunctive plan into a single committed next step before recording it as an active intention.

## Risks / tensions

- The paper assumes a single-threaded reasoning agent with a consistent belief set. Navi-Brain is event-driven and may hold stale or inconsistent beliefs briefly; naive dependency-release could thrash intentions — an intention whose backing belief flickers would be released and re-adopted in a tight loop. Release checks need hysteresis, a minimum-hold duration, or a confirmation cadence (the paper's own `BEFORE` operator is temporal, not instantaneous, so this is consistent with the formalism). The monotonic fencing tokens in `src/Model/CycleRun.php` could be repurposed to enforce a minimum-hold window.

- The screen-of-admissibility theorem depends on the agent *believing* `a` defeats `b`. Belief here is not the same as the paper's idealized modal logic — Navi-Brain beliefs are records with confidence, not closed-world modal truths, and the agent may not have registered the conflict at all. Conflict detection will be heuristic and best-effort, not sound. This is acceptable: the paper gives a *specification* for ideal behavior, and Navi-Brain implements a bounded approximation.

- Social-commitment interlock (`Section 8.2`) is the most speculative part of the paper and overlaps with BDI and game-theoretic work Navi-Brain has not committed to. Treat as design reference for future multi-agent or human-to-agent extensions, not a current implementation target.

- The paper is a logic specification, not an engineering study — no empirical evaluation, no ablation. The properties it proves hold in its model, but the model's assumptions (single course of events, deterministic agents, no simultaneous actions, no branching time) are strict. The useful output is the *specification*, which the authors explicitly say should be embodied in architecture rather than used as an online reasoner.

- Implementation must stay within existing safety invariants: dependency-aware release is *more* corrigible, not less, because it adds additional justified-release paths. But the release resolver itself must be bounded and auditable — it should not silently promote new commitments, invoke remote models (see `src/Core/FreeModelWorker.php` boundaries), or write procedural memory. The user-authority-outranks-intentions invariant means a `release_condition` tied to user goal-withdrawal must fire before any other release path.

- The paper's "agents are not nondeterministic" result (Proposition 5.4) implies that an agent believing it is about to do a disjunction must believe it is about to do one specific branch, or believe in a common initial step. This is philosophically loaded — it commits Navi-Brain to resolving disjunctive intentions into concrete next-actions before acting, which is fine for this system but would be a real constraint if conditional plans were ever represented as first-class intention structures.

## Bottom line

**Adopt the relativization and admissibility results; monitor the social-commitment interlock.** The single most important consequence for Navi-Brain is dependency-aware release: intentions that drop automatically when their justifying beliefs or supergoals evaporate. That closes the gap between "persistent commitment" and "blind fanaticism" the paper spends its second half diagnosing, and it costs one resolver loop in the reflection pass plus a small schema extension to `Intention.php`. The paper's formalism fits the existing `Intention.php` shape so tightly that the main work is operational, not conceptual — the fields are there, the heartbeat is there, the missing piece is the code that reads them together.
