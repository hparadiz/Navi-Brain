# Record #51 — OMNI: Open-endedness via Models of human Notions of Interestingness

Zhang, Lehman, Stanley, Clune. arXiv:2306.01711v3 [cs.AI], 15 Feb 2024. 47 pages.
The PDF carries no venue banner — treat as preprint as filed.

## 1. Mechanism

OMNI is an auto-curriculum for task-conditioned RL. It does not change the RL
algorithm (PPO + GAE throughout, p.28, p.29). It changes only the probability
distribution `D` over which task the agent trains on next. Two terms multiply
into `D`: a statistical learning-progress term and a binary foundation-model
verdict.

### 1.1 The learning progress (LP) term

Extends Kanitscheider et al. (2021), dropping their dynamic exploration bonus
(p.4). Per task `t`, maintained as two floats:

1. Once, before training: measure `p_rdn(t)`, the success rate of a **random
   action policy** on that task (p.20, Algorithm 1 p.27).
2. Every `N` policy updates, evaluate the current policy on **every task in T**
   to get `p_raw(t)`.
3. Normalize against the random baseline — the paper's own contributed
   extension: `p_norm = (p_raw - p_rdn) / (1 - p_rdn)` (p.20).
4. First EMA: `p_recent = β·p_norm + (1-β)·p_recent`, with β = 0.1 (p.20).
5. Second EMA over the first: `p_gradual = β·p_recent + (1-β)·p_gradual`.
   `p_gradual` is a deliberately laggy copy of `p_recent`.
6. Reweight both through `f(p) = (1 - p_θ)·p / (p + p_θ·(1 - 2p))`, `p_θ = 0.1`
   (p.20). `f` magnifies differences at low success probability and compresses
   them at high success probability, and also compensates for the EMA's
   temporal lag (p.4).
7. `LP(t) = |f(p_recent(t)) - f(p_gradual(t))|` (Algorithm 1, p.27). The
   absolute value makes it **bidirectional**: a task whose success rate is
   *falling* scores as high as one that is rising, explicitly "to also focus
   learning on tasks where performance is degrading due to forgetting" (p.5).
8. Convert LP across tasks into sampling weights: z-score, sigmoid, normalize
   to a probability distribution (p.20).

Note a typo in the prose formula on p.20 (`LP = |f(p_recent − f(p_gradual)|`,
unbalanced parens); Algorithm 1 on p.27 gives the correct expression.

Ablation of step 3 alone (`LP-no-norm`, Crafter, 30M steps, 10 seeds) shows the
random-baseline normalization is worth a significant gain on its own (p.20).

### 1.2 The Model of Interestingness (MoI) — what it is prompted with and returns

The MoI is an LLM used as a **binary relative-redundancy classifier**, not a
scorer and not a generator (in the finite-task version).

Prompt contents (p.5), verbatim structure from Appendices B (Crafter, GPT-3
davinci, few-shot, p.21-22) and C (BabyAI, GPT-4, system prompt + 3 chain-of-
thought examples, p.22-24):

1. A directive: "The ultimate goal that [the agent] would like your help with is
   to learn as many interestingly different skills as possible ..." (p.5, p.22).
2. An environment description — object types, colors, how a task is written.
3. `Tasks the agent currently do well: <list>` and
   `Predict which of these tasks are interesting: <list>`.
4. Criteria text: "Interesting tasks are roughly those that are sufficiently
   different from the ones that it can already do, and should be novel, diverse
   and at least worth learning." (p.22)

Return format (p.22-23): a free-text `Reasoning:` block, then `Predictions:` —
one line per task, `"<task>": True` or `False`. Nothing numeric. GPT-3 "nearly
always conforms"; on malformed or missing entries the response is regenerated
with only the missing tasks resubmitted (p.22).

### 1.3 How the verdict enters task selection

Two-stage, and the ordering matters:

- **Partition** (Algorithm 2, p.27-28). The FM is never asked to rank the whole
  set. Instead: sort tasks by EMA-smoothed success rate; take the highest-
  success **uncategorized** task and put it in the interesting set *by
  construction, with no FM call*; then prompt the FM with the interesting set as
  "tasks done well" and the remaining uncategorized tasks as candidates; move
  everything the FM marks boring into the boring set; repeat until every task is
  categorized. The anchor is chosen deterministically by success rate; the FM
  only ever answers "which of these are redundant given this set" (p.27).
- **Reweight**: `p_moi(t) = 1 if t ∈ T_int else 0.001`; then
  `D ← p_lp ⊙ p_moi`, normalized to sum to 1 (p.5, Algorithm 1 p.27).

So the MoI is a **1000× multiplicative down-weight applied after LP, never a
veto and never a nominator**. A misjudged task still gets sampled about one time
in a thousand.

### 1.4 The infinite-task-space variant (Section 5)

Different mechanism, same principle. GPT-4 is prompted zero-shot (no few-shot
examples — "our testings found that they were not needed", p.25) with
`Tasks the agent currently does well:` (success > 0.6) and
`Tasks the agent cannot do yet:`, and returns three things in one response
(p.9, p.25):

1. `Reasoning:` free text,
2. `Next tasks in natural language:` three proposed tasks,
3. `Next tasks as sequence of environment states:` the **machine-checkable
   completion predicate for each**, e.g.
   `[[obj_attributes("Potato","visible":True)], [obj_attributes("Knife","visible":True)], [obj_attributes("Potato","isSliced":True)]]`
   (p.10-11).

The predicate is data, not code — a closed set of 11 attributes over a fixed
object list — and it *is* the reward function. "This version of OMNI integrates
the generation of the task and the code requirements for task completion into a
single output" (p.9). Here the FM does nominate goals; LP then runs over the
growing set.

## 2. Transferable to Navi-Brain

**(a) The EMA-of-EMA bidirectional learning progress estimator.**
`docs/ongoing-cognition.md` line 345 already commits to "controllable learning
progress rather than raw novelty" but gives no formula. This is a formula, and
it is four floats and ten lines of PHP. Concretely: add to whatever candidate
record the agenda scores (per `(thread_id, operation)` pair is the natural
grain, given `thread_steps.operation` and `thread_steps.status` already exist in
`src/Model/ThreadStep.php`) the columns `p_recent`, `p_gradual`, `baseline_rate`,
`lp_updated_at`. On each completed step, feed `status = 'succeeded'` as a 0/1
observation, normalize by `baseline_rate`, run the two EMAs, and store
`LP = |f(p_recent) - f(p_gradual)|` with `p_θ = 0.1`, `β = 0.1`. No training, no
model call, no GPU.

*What does not transfer cleanly:* OMNI re-evaluates the policy on **all** tasks
every N updates (Algorithm 1, p.27). Navi-Brain cannot re-run an operation to
sample its success rate; it gets one noisy observation per actual execution. So
the EMAs will update at wall-clock rate, not at eval-interval rate, and will be
high variance for a long time. Cheap degraded version: raise β (faster, noisier)
and require a minimum observation count before LP is allowed to contribute more
than a fixed floor to the agenda score.

**(b) Normalization against a null baseline.** `(p_raw - p_rdn)/(1 - p_rdn)`
(p.20). The Navi-Brain analogue of `p_rdn` is: how often would this operation's
postcondition have held anyway, without running it. This is the thing that stops
"the file already existed" and "the check was already green" from registering as
progress. It can be a hand-set constant per operation type initially.

**(c) The multiplicative-with-floor combination rule.** Two properties worth
stealing regardless of whether interestingness itself is adopted: an
interpretive term (i) only re-weights candidates the mechanical term already
nominated, and (ii) never zeroes anything, so a wrong verdict is recoverable.
Any LLM-derived agenda term should enter as a bounded multiplier with an
explicit floor, applied *after* nomination and *after* the authority gate.

**(d) Task-and-predicate as a single worker output.** The §5.1 output schema —
proposal plus its own machine-checkable completion predicate, in the checker's
own vocabulary — is the single most directly implementable idea here. It
instantiates two existing plan commitments at once: "each cognitive operation
must name an expected postcondition" (plan line 332) and "verification returns
the observed predicate and evidence, not a self-report" (plan line 370). Map it
onto `thread_steps.expected` (the goal), `thread_steps.deterministic_checks`
(the predicate), `thread_steps.observed_result` (the evaluation). Keep OMNI's
constraint that the predicate is *data over a closed attribute enum*, never
executable text.

**(e) Algorithm 2's question shape.** Never ask a model to score. Ask a binary,
relative, set-contextualized question — "which of these candidates are redundant
given this set" — and re-anchor the comparison set deterministically between
calls. This is exactly the kind of question a free or local model can answer
reliably, and it makes the output auditable: a label, plus the comparison set it
was labelled against, plus the prose reason. Store all three.

**(f) The cheap substitute the paper itself validated.** Appendix Q (p.44)
replaces the FM with sentence embeddings (`all-mpnet-base-v2`) plus OPTICS
clustering: same tasks are same cluster, same cluster is boring. When the boring
tasks were repetitive numeric variants, the embedding MoI was **statistically
indistinguishable from the FM MoI** (all p > 0.05, p.44). It only lost when
boring tasks were compounds requiring reasoning about what the agent already
knows (p.44). Navi-Brain's realistic failure mode — re-proposing a near-identical
operation it just ran — is the *first* case. So the cheap version is not merely
acceptable, it is what the paper's own control says suffices. A local embedding
model, or in the smallest version normalized-string/stem dedup over
`thread_steps.operation` + target, buys most of the benefit at zero model cost.

**Cost profile of the FM call itself, for the record.** The FM cost is the small
part: $0.02/1k tokens for davinci, $0.03/1k for GPT-4, "extensively cache[d]"
and reused across all 10 seeds (p.22, p.24). But that is only cheap because the
task set is fixed, finite, and shared across runs. Algorithm 2 issues one prompt
per interesting task discovered, each listing every still-uncategorized task, so
tokens per curriculum update scale as O(|T_int| × |T|). For Navi-Brain's agenda —
maybe 5 to 20 candidates per wake — that is a handful of small prompts. This
part is genuinely affordable. Everything else is not (see §5, §6).

## 4. Challenge to the current plan

**The plan's nomination rule and OMNI's finite-task MoI are compatible; the
plan's nomination rule and OMNI's *infinite*-task variant are not.** In the
finite version the MoI never proposes anything — it re-weights an enumerated set
(p.5, p.27). That is fully compatible with "nominate candidates only from
discrepancies, opportunities, due needs, and authorized events" (plan lines
452-453). Section 5 is a different animal: GPT-4 invents goals that derive from
no discrepancy, no due need, and no authorized event (p.9). It works — 13 tasks
learned vs 2 for LP and 0 for uniform (p.12) — and it should still be rejected,
not for ineffectiveness but because it relocates goal origination into a free-
model prose channel upstream of the authority gate. Take the filter, not the
generator.

**Is the interestingness term a defensible addition, or an unfalsifiable
aesthetic criterion?** In *this paper* it is falsifiable, for two specific
reasons that Navi-Brain does not currently have:

1. There is an external metric that interestingness is not allowed to define.
   Headline numbers are computed on the **full** task set including all the
   boring tasks (p.7). Interestingness is a means; success on everything is the
   end. That is the right shape and it is why the claim is not circular.
2. They built an oracle (OMoI) and measured the FM against it (p.8, p.33).

Navi-Brain has neither. There is no held-out task set to evaluate over, and the
paper itself concedes that "constructing such models in more complex domains
will not always be feasible, nor would it scale well given the human labor
required" (p.33). Absent both, an interestingness term in Navi-Brain's agenda
score would be exactly what the brief fears: a float nobody can be wrong about.

**And the paper's own worst result says the FM's taste is not autonomous.** The
boring tasks were authored by the researchers — 90 numeric repeats and 1023
always-fail distractors (p.6) — so the main experiment asks the MoI to
re-discover a partition its designers had already drawn. In the one setting
where the authors had *not* pre-agreed with the model (synonyms, Appendix O),
the MoI was wrong: it labelled "gather wood" boring given "collect wood",
correctly for a language-prior-having agent and incorrectly for a bag-of-words
one. Result: "OMNI does not outperform LP on all metrics" (p.38), and "the
oracle significantly outperforms OMNI: LP + MoI on the set of all tasks" (p.39).
The fix was a human editing the prompt to tell the model about the agent's lack
of a language prior (p.39). Honest reporting, and it costs them the strong claim:
the MoI has a notion of interestingness that matches the researchers' *after the
researchers explain what they mean*. For Navi-Brain, where nobody is standing by
to patch the prompt at 3am, that is the failure mode to plan around.

**The plan's LP-over-novelty preference is right, and OMNI's own numbers
under-sell how right.** The ablation that isolates MoI from LP is LP vs LP+MoI,
and it is a second-order effect. Crafter: Uniform 4 tasks → LP 55 → OMNI 82
(p.7-8). LP over Uniform is ~14×; MoI over LP is ~1.5×. BabyAI: 1 → 4 → 8. The
AI2-THOR jump (0 → 2 → 13, p.12) is not this ablation at all — there the FM is
generating tasks, not filtering them. **If Navi-Brain builds one of these two
mechanisms, build the LP estimator.** There is also no `Uniform + MoI` arm
anywhere in the paper, so OMNI cannot claim interestingness helps *without* a
progress signal underneath. It is a modifier, not a substitute.

**A real complication for the stagnation rule.** OMNI's LP is bidirectional by
design: `|Δ|`, so a degrading task is sampled *more* (p.5). The plan treats
regression and repeated op/result pairs as a typed stagnation discrepancy whose
response is "re-observe, wait, postpone, or escalate — not a tangential quest"
(plan lines 379-382). These two pull opposite ways on the same signal. A
background loop that samples harder wherever things are getting worse is a
budget incinerator on a single workstation. Recommendation: keep LP
bidirectional for *detection*, but route the falling branch to escalation or
re-observation rather than to increased sampling weight. That is a divergence
from OMNI, and it is the right one.

**Goodhart, conceded by the authors.** "By Goodhart's law, we expect that any
model will have pathologies uncovered once it is a target metric being optimized
against" (p.13). The plan already insists score components "remain inspectable
instead of disappearing into one survival-flavored reward" (plan line 351). An
FM interestingness float is the least inspectable component available. If it is
adopted at all, it must be stored as a discrete labelled verdict carrying model
identity, the comparison set it was judged against, and the prose reason — a row,
not a number.

## 5. Evidence quality

**Domains.** Three: Crafter with the survival component **removed** and "sleep"
and "place plant" deleted (p.6); BabyAI MiniBossLevel, chosen over BossLevel for
speed (p.6); AI2-THOR, a single kitchen floorplan with simplified action
targeting — the target object is auto-selected rather than specified by the
agent (p.10).

**Task pools.** Crafter: 15 interesting + 90 boring (numeric repeats) + 1023
"extremely challenging" tasks the agent is *assumed* to always fail and is
therefore hard-assigned success rate 0 (p.6). BabyAI: 1364 tasks. AI2-THOR:
unbounded.

**Sample size.** Main results: 10 seeds per arm, 100M env steps (Crafter,
BabyAI), 1M steps (AI2-THOR). Appendix settings run at 30M steps × 10 seeds
(LP-no-norm p.20, compound p.35, synonyms p.38, embedding-MoI p.44). The
survival-retained Crafter setting is the thin one: 30M steps × **3 seeds**
(p.43-44).

**Compute.** ~33 h/run Crafter, ~60 h/run BabyAI, ~24 h/run AI2-THOR, each on a
24GB NVIDIA A10 with 30 vCPUs (p.7, p.12). Main results alone are
10×33 + 10×60 + 10×24 ≈ **1170 A10-GPU-hours**; the appendix arms add several
hundred more. Navi-Brain has no GPU budget of this kind and no weights to
update, so nothing downstream of the curriculum transfers — only the curriculum
arithmetic does.

**Statistics.** Mann-Whitney U at 25/50/75/100% of training; 95% median
bootstrap CIs from 1000 resamples. Multiple comparisons (4 checkpoints × 2
metrics × 2 task subsets × several settings) are uncorrected, but headline
p-values are < 1e-3, so the main conclusions survive any reasonable correction.

**Baselines.** Uniform; LP-only; LP + oracle MoI (p.33); LP + embedding MoI
(p.44); LP-no-norm (p.20). That is a genuinely respectable set — the oracle and
the embedding control are more than most papers of this type offer. Missing:
any `MoI without LP` arm; any hand-designed curriculum; and any trivial
string-similarity dedup baseline, which given the Appendix Q result would
probably have done well.

**Where the metric is soft.** The 1023 always-fail tasks are dead weight that
depresses the Uniform arm far more than the others; a uniform-over-plausible-
tasks control would look less catastrophic. And the Crafter "boring" tasks
("collect 2 wood" … "collect 10 wood") are not merely uninteresting, they are
strictly harder duplicates of interesting ones, so down-weighting them is partly
down-weighting pointless difficulty rather than boredom. The "interesting tasks
only" plots (p.30, Figure 9) are computed over the treatment's own target subset
and are close to circular in isolation; the all-task plots are what saves the
claim, and the authors do lead with those.

**Contamination not discussed.** Crafter and BabyAI are public benchmarks with
published technology trees and task grammars. GPT-3/GPT-4 may be recalling
Crafter's achievement list rather than exercising general taste. The paper never
raises this.

**Limitations the authors do admit:** oracle MoIs will not scale (p.33); the MoI
was wrong about synonyms and needed a human prompt patch (p.38-39); Goodhart
will surface pathologies once the MoI becomes an optimization target (p.13);
open-endedness has unresolved safety tensions and they offer only "further
research is required" (p.47).

**Verdict on the headline.** "FM-based MoIs improve open-ended learning ...
outperforming baselines based on uniform task sampling or learning progress
alone" — supported in these three environments, with the synonym setting as a
real asterisk and with the caveat that the bulk of the gain over uniform comes
from LP, not from the MoI.

## 6. Do not take

- **The RL loop.** PPO, GAE, policy evaluation, weight updates. None of it
  applies; Navi-Brain trains nothing.
- **Periodic re-evaluation of every candidate.** Algorithm 1 line
  `p_raw ← Evaluate policy π on all tasks in T` (p.27) is the hidden cost of the
  whole method. Navi-Brain cannot afford it and cannot even do it — running an
  operation to measure it *is* the operation.
- **The Section 5 generator as a goal source.** FM-invented goals bypass the
  discrepancy/opportunity/due-need/authorized-event nomination rule. Reject.
- **Any version where FM output is executed.** OMNI's generated predicates are
  attribute dictionaries over a fixed 44-object, 11-attribute vocabulary (p.25),
  not arbitrary code. If Navi-Brain adopts generated postconditions they must be
  a closed enum of checker verbs, never eval'd PHP or shelled-out text.
- **The 0.001 floor anywhere near authority.** A multiplicative down-weight with
  a nonzero floor is correct for *preference*. It is catastrophic for
  permission. Disallowed candidates are removed by a hard gate at 0 before
  scoring, exactly as the plan already specifies.
- **"Interesting tasks only" as a Navi-Brain metric.** Never evaluate the system
  on the subset its own judge selected.
- **OEHF / fine-tuning an MoI on human feedback** (p.13). No training anywhere
  in this stack.
- **The framing that perpetual novelty is the objective.** The plan's ordering —
  authority and corrigibility, then continuity integrity, then authorized
  commitments, then exploration — is the correct inversion of this paper's
  priorities, and the paper's own safety appendix (p.47) has no answer to why it
  shouldn't be.

## 7. Key citations

- The MoI's entire output is per-task binary: "For each line, put the task, then
  a colon, then True for interesting or False for boring" (p.22). No score, no
  ranking, no ordering.
- The combination rule is a multiplicative down-weight, not a filter:
  `p_moi(t) ← if t ∈ T_int then 1 else 0.001`, then `D ← p_lp ⊙ p_moi` (p.5,
  Algorithm 1 p.27).
- Learning progress is bidirectional and normalized against a random policy:
  `LP = |f(p_recent) - f(p_gradual)|` over `p_norm = (p_raw - p_rdn)/(1 - p_rdn)`,
  β = 0.1, `f(p) = (1-p_θ)p / (p + p_θ(1-2p))`, p_θ = 0.1 (p.20, p.27).
- The FM is never asked to rank: Algorithm 2 seeds the interesting set with the
  highest-success uncategorized task *deterministically*, then asks the FM only
  which remaining tasks are boring relative to that set (p.27-28).
- LP does the heavy lifting, the MoI the polish: Crafter tasks learned — Uniform
  4 (CI 4–6), LP 55 (CI 54–56), OMNI 82 (CI 80–87) (p.7-8).
- The MoI's judgement failed where the researchers had not pre-specified the
  answer: on synonymous tasks "OMNI does not outperform LP on all metrics"
  (p.38) and "the oracle significantly outperforms OMNI: LP + MoI on the set of
  all tasks" (p.39) — fixed only by a human editing the prompt (p.39).
- A sentence-embedding + OPTICS clustering MoI was statistically
  indistinguishable from the FM MoI when boring tasks were repetitive variants
  (all p > 0.05), and only lost on compound tasks (p.44).
- Cost: 100M steps, 10 seeds, ~33 h/run Crafter and ~60 h/run BabyAI on a 24GB
  A10 with 30 vCPUs (p.7); ~24 h/run for AI2-THOR (p.12). FM calls were cheap
  ($0.02–0.03 per 1k tokens) only because the task set was fixed and responses
  were "extensively cache[d]" and reused across all runs (p.22, p.24).
- The authors concede the mechanism will break under optimization pressure: "by
  Goodhart's law, we expect that any model will have pathologies uncovered once
  it is a target metric being optimized against" (p.13).
