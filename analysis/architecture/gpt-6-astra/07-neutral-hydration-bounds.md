# Neutral reads and the byte cost of sparse dreaming

The routine maintenance path does not rescan the whole native corpus for every unchanged slot. Its remaining recurring cost is reconstructing complete selected records before PHP extracts a small claim or evidence projection. Sparse dream preparation adds bounded record selection and recovery, but a record-count limit is not a bound on copied bytes or all native posting work. This report is a source audit of the 2026-09-07 working tree, with no live requests, fixtures, runtime tests or timing measurements.

## What a neutral source read does

`Memory::inspectByID` calls `TokenMemoryDaemon::fetch` without counted access. The native `memory_find_id` uses the global sorted ID index, so lookup is O(log M), not a resident-memory scan. `append_record_wire` then serializes metadata and copies all decoded content bytes from stored token segments into the response under the engine mutex. The cached decoded byte count avoids a sizing prewalk, but it cannot remove that full content copy. Neutrality suppresses the read/learning accounting; it does not imply a metadata-only response. [Memory](../../../src/Model/Memory.php), [transport](../../../src/Storage/TokenMemoryDaemon.php), [native engine](../../../memories/src/tokmem.c).

The PHP `exchange` method collects the complete response payload. `decodeRecords` takes separate `substr` slices for metadata and content, decodes the positional fields, and retains each content string in a hydrated record. PHP object/array sharing and allocator behavior affect the actual peak, so this audit does not assign a fixed copy multiplier. Structurally, the complete response and extracted content exist across the decode boundary; truncating a claim afterward does not prevent their construction.

Native content and total response limits are each 64 MiB. The response also needs record headers and metadata, so a content record near its individual limit need not fit as a complete response. A batch of individually valid records can exceed the aggregate response bound. The original PAGE/LIST command failed the whole response in this case, so ingestion could repeatedly select the same failing page without advancing its cursor. The bounded commands now return a whole-record prefix when at least one record fits, as detailed below. A single unrepresentable first record still fails explicitly; unbounded LIST and explicit BATCH still fail as a whole.

## The actual paths and their limits

Let L be the configured dream source limit, 1–32 with default 32, and S the workspace slot limit, 1–128 with default 32. These limits count selected rows or sources, as qualified below.

| Path | Selection performed | Full-content work that remains |
|---|---|---|
| Unchanged native workspace upkeep | At most S canonical slots selected in one short SQLite snapshot; persistent priority/audit cursors survive process restart | An eligible active memory/procedure slot fetches its complete backing record to derive the first 800 characters, confidence and validity. Its projection is separately fetched for exact identity/content/metadata comparison. Inactive slots can still require a projection read. |
| Pending workspace projection replay | Selected slot's journal, under its scope/role lock | Reads and applies the current projection, then later maintenance can reread canonical state, backing source and projection. These reads occur across separate freshness/ownership boundaries and cannot all be removed as duplicates. |
| New dream episode admission | Ascending and recent-tail native pages split L between them; default 16 + 16 | Full episodic records arrive before evidence classification. A newly encountered ledger ID can also fetch one complete semantic record through source-memory provenance, although admission consumes only its identity and expiry. The two admission pages can overlap. |
| Fresh dream batch selection | At most L pending IDs; stop after 12 accepted sources | Individual full episode fetches, possibly repeating records just admitted. Similarity filtering and projected evidence sizing happen after hydration. The selected seed record remains available for subsequent comparisons. |
| Same-preparation v2 dispatch | Exact claimed-work/manifest binding to the ephemeral prompt | No immediate source rereads are needed solely to reconstruct the prompt. The final prompt digest and byte cap are still checked. |
| Cold/restarted v2 dispatch | At most 12 ordered source references | Up to 12 individual full-record neutral reads, then projection/hash/eligibility checks. Only the final prompt is limited to 16 KiB. |
| Stored-result recovery before selection | Up to L queued-ledger rows and L dedicated-lane work rows | Each unsettled completed result can enter integration, with its own full source rereads and potentially a native semantic candidate query. Already settled results exit early. At most 2L selected work candidates is an upper bound, not a claim that all reach expensive integration. |
| Grounded claim integration | Full observed source batch revalidated; native reuse query returns at most 100 semantic records when needed | `Memory::rankCandidates` traverses relevant token postings before its output limit, then decodes the selected complete records. Creating a new assertion also performs the ordinary durable native write path. |

## Indexed selection versus corpus-dependent work

The exact tier/status combination used for episodic admission selects `MemoryFilterIndex.id_order`. Ascending PAGE uses a binary search for `after_id` followed by the selected page; recent LIST starts at that index's tail. Those paths do not walk unrelated tiers or decode every memory. `provenance_memory_record` binary-searches a source-ID index, locates the range with that source ID, then searches backward for the latest eligible matching record. A very large number of siblings sharing a source ID can make that lookup expensive, even though only one complete record is returned. TTL is checked by PHP after the native tier/status match.

`maintainBatch` explicitly defers pointerless legacy projections. Its `findProjection(..., false)` path cannot silently invoke the foreground legacy scan across all active working memories. The separate compatibility scan remains available to explicit/foreground recovery, so this is a bound on the routine path rather than a removal of legacy functionality.

The native `query_memories` path used by `RANK_RECORDS` calls `score_postings` for cue constituents, roots and bounded linked-token neighbors. Each posting list can still contain many memories. Tier/status predicates and the top-k output bound are applied after touched candidates have been gathered. Consequently, a 100-record semantic result limit does not limit posting visits or touched memories to 100; in the worst case the relevant posting lists reach much of the corpus. This route is reached by some grounded integrations and their recovery, not by every unchanged workspace check.

Native writes have separate history-dependent costs. Metadata changes maintain sorted resident indexes and publish durable files; they are not O(1) merely because content is immutable. The resident-ID maximum scan during new allocation has now been removed, and the receipt maximum gained an index. Those narrowly accepted changes, their ordering proof and index storage/startup cost are documented in [report 05](05-native-publication-capabilities.md).

## Removed repeated prompt sizing

Fresh selection formerly copied the growing row array and rendered the entire candidate prompt to check every candidate's size. Cold reconstruction likewise rerendered the accumulated prefix at each step. Both paths now initialize their byte count from the unchanged empty-list renderer and add only the next row's exact encoded length plus a comma when a prior row exists.

For a flat JSON list, the empty representation already contains both brackets. If B is the byte length of the instructions plus `[]`, and Eᵢ is the byte length of row i encoded with `JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE | JSON_THROW_ON_ERROR`, then n accepted rows occupy exactly B + ΣEᵢ + max(0, n − 1). Rejected oversized candidates do not advance the retained count. Row field order and integer/string values are unchanged, and each row is encoded before acceptance at the previous validation boundary. Previously accepted rows are immutable during the loop, so omitting their repeated encoding does not mask a later encoding error.

The final renderer, 16 KiB cap, source order, projection/version and full-prompt hash remain unchanged. No source fetch was removed by this arithmetic change. It removes repeated growing-prefix JSON serialization and the preparation array copy; it does not eliminate evidence projection or the final render. With n at most 12, this is a bounded structural improvement, not a measured CPU or latency result. PHP syntax and whitespace checks passed; no runtime equivalence test was performed.

## Implemented aggregate-page progress repair

`append_record_wire` distinguishes response-capacity exhaustion with the named `RECORD_WIRE_CAPACITY_EXCEEDED` result. Invalid cached content length, record-header formatting and decoded segment validation remain failures. All existing callers other than bounded `list_memory_records` continue to treat every nonzero result as a failure.

For a positive row limit, `list_memory_records` keeps exactly the original selection order and appends complete frames until the next frame exceeds response capacity. If at least one frame was emitted, it returns that nonempty prefix and compacts the batch-count header to the actual emitted count. It never skips the failed record to pack a later one. Full responses retain their original header without an extra body move. Counted read accounting runs only after successful final framing, over exactly the emitted records; other errors retain the previous no-counted-partial-response behavior.

The first-record edge requires a separate check: a selected-count header such as `1000\n` can consume more bytes than the actual one-record header `1\n`. On capacity exhaustion before the first frame, the implementation retries that same record once with the shorter header when any bytes can be recovered. If it fits, exactly that one whole record is returned. If it still fails, the command remains an error, rather than returning an empty page or moving the cursor past the source. A shortened final header can leave unused capacity; the contract is an ordered prefix up to both bounds, not maximum byte utilization.

The native engine validates immutable token vectors and decoded lengths when records become resident. As before, `append_record_wire` checks available capacity before decoding that frame's segments; this change does not add a validation scan of withheld records. Every emitted record still passes the existing full segment/count validation. A reached invalid-record failure remains an error, not a prefix-success condition.

Two existing legacy readers inferred exhaustion from a short page: `ProceduralMemory::findLegacy` stopped below 256 rows, and `WorkingMemory::findProjection` stopped below 100. Both now continue after the last returned ID until an empty page. Without that coordinated change, the new daemon could make an old scanner miss a later procedure or duplicate workspace identity. Updated readers also work against an old daemon, but cannot recover its aggregate-cap errors. Dream admission already advances only to the last observed ID, so its source-coverage cursor needs no semantic change. The other bounded LIST callers consume selected windows without treating short counts as proof of complete corpus traversal; unbounded scans retain their old failure behavior. See the [protocol contract](../../../memories/README.md).

The same 60-second wall, 30-second CPU and 1 GiB address-space caps were used as for the allocation review. ## Narrow follow-ups and their proof obligations

`consolidationSimilarity` repeatedly projects and normalizes the same seed. Accepted candidates are projected again immediately for hashes and packing; integration also reprojects already retained observations during grounding. A local reuse of projection strings or seed features could remove repeated parsing within one observation. It would need to preserve the current type-mismatch early return, exact normalization/command/token thresholds and error behavior. Reusing text across the later integration freshness check would instead erase an intentional observation boundary. No such reuse is implemented by this report.

A metadata-only provenance response could avoid decoding semantic prose when admission only needs identity/expiry. A bounded source-projection response could reduce full record hydration, but the existing projection understands machine/action syntax, retains arbitrary observed output and otherwise truncates by Unicode characters. A raw byte prefix is not equivalent. Either optimization needs a separately versioned protocol, full-record validity semantics, compatibility behavior and an explicit truncation/projection contract; merely exposing native token IDs would not supply those guarantees to PHP.

The whole-prefix repair resolves aggregate-cap stalls when the next first record can fit alone. It does not solve an individually unrepresentable record, impose a smaller per-cycle byte target, or make all source sizes cheap. Those remaining constraints require an explicit projection/transport policy; silently skipping oversized evidence would falsely claim coverage.
