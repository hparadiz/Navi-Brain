# Working-memory source references

Working-memory `record_type=memory` and `record_type=procedure` both address a **native Memory ID** in `record_id`. Neither addresses the SQLite `procedures.id` namespace. Native procedural records and executable SQLite Procedure definitions are linked separately through `Procedure.memory_id`; workspace presence does not authorize execution or bypass generation/dispatch guards.

`memory` is deliberately generic: active, unexpired episodic, semantic and procedural native records are valid. Decision retrieval currently publishes its first nonworking result under this type, including a procedural result. `procedure` is narrower: it requires an active, unexpired native procedural record. Working-tier records, missing sources, invalid expiry values and wrong-tier procedure references are omitted during current snapshot/incumbent hydration and expired by bounded canonical maintenance. Existing IDs are never guessed or translated across SQLite/native namespaces.

Capsule candidate selection separately reserves its memory pool for episodic/semantic evidence and its procedure pool for procedural records. Both pools filter current status and expiry before a new contest. Historical capsules retain exactly their original serialized claims for audit; they are not rewritten by source hydration. Current incumbents come from the mutable working-memory hub. The procedural candidate scan retains its existing bounded window and counted-read behavior; expiry filtering may leave fewer candidates rather than scanning an unlimited backlog.

`working_memory.write` accepts caller-supplied references through the existing procedural adapter; the reference is not proof that the caller's claim equals its backing source. Current memory-backed hydration renders the referenced source and enforces the typed eligibility contract. Privacy-safe snapshots omit both native-memory-backed reference kinds before hydration, so a permitted role cannot use hydration to undo a redacted summary. Other record types retain their existing subsystem-specific behavior.

Maintenance uses independent priority and audit ID cursors. Active slots or any pending projection journal receive the priority budget; settled inactive slots retain at least one audit position per nontrivial batch to detect native projection drift. A batch of one alternates the two queues, with an empty-side fallback. Both queries wrap at most once, and duplicate IDs that move between queues during selection are processed once. The total visited count remains within the configured limit. `after_id` means the last ID actually visited; `priority_after_id` and `audit_after_id` expose the two separate cursors.

This preserves inactive projection repair: settled inactive rows cannot simply be excluded, because `synchronizeProjection` checks and repairs their native projection even when canonical fields do not change. Pointerless rows remain deferred from the bounded lane, including crash states before a first projection pointer; existing foreground recovery owns their broader legacy search. Local-file locks serialize projection replay for cooperating processes using the same checkout lock directory, not separate lock roots sharing a store.

Validation here consists of source tracing, PHP lint and diff checks. No live-store probes, runtime tests or measured performance claims were used.
