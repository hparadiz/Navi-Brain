# Online inference options for Navi cognition

Research snapshot: **2026-09-06**. Official provider documentation and the current repository clients were inspected. No accounts were created, payment methods added, credentials read, inference requests submitted, services changed, or private prompts transmitted. The Cerebras public model catalog was fetched without authentication. Prices and limits below are provider-published facts at this snapshot; throughput figures are provider claims, **not measured latency from this machine**.

## Recommendation

Use **direct Groq, pinned to `openai/gpt-oss-120b`, as the first synthetic-only pilot candidate** if an authorized free account is available. Its documented strict schema mode matches the proposal workflow, it avoids an extra routing intermediary, and its published free allowance is sufficient for a small comparison. Keep local inference as the default for private cognition until an explicit egress policy and the relevant account's data controls are verified. This is a recommendation, not an enabled route. Groq documents strict constrained decoding for this model. [Groq structured outputs](https://console.groq.com/docs/structured-outputs).

**Cerebras is the second candidate for a paid latency comparison**, subject to a spending decision. Its current offering is a time-limited credit trial requiring a payment method, not renewable free inference. **OpenRouter is the third candidate for controlled model comparison or provider availability**, with model/provider pinning. An automatically changing free-model pool would make quality and latency comparisons harder to interpret. [Cerebras limits and trial terms](https://inference-docs.cerebras.ai/support/rate-limits), [OpenRouter routing](https://openrouter.ai/docs/guides/routing/provider-selection).

**Illustrative arithmetic, not a workload measurement:** a call with 2,048 input and 256 billed output tokens costs approximately $0.000461 on Groq or $0.000909 on Cerebras at the listed rates. At one call every five minutes, 288 calls/day consume 663,552 tokens and cost about $3.98 or $7.85 per 30 days respectively. That exceeds Groq's quoted free daily token allowance; the same token assumption allows about 86 such calls/day there before other constraints. These estimates exclude extra reasoning tokens, retries, tool charges, taxes, and any routing fees. The actual prompt lengths and billable output must be measured. For a proposed OpenRouter route, use an explicit provider allowlist, `allow_fallbacks: false`, `data_collection: "deny"`, `zdr: true`, and `require_parameters: true`. These are requested policy constraints, not a measured privacy guarantee. The routing reference explicitly supports ZDR enforcement, while the provider-logging page still contains a contradictory statement that routing does not change with retention policies. Prefer the specific routing API documentation for configuration, and verify the selected endpoint/account policy before private traffic. ## API compatibility and repository seams

All three expose a chat-completions shape with bearer authentication, but they are not drop-in replacements for the current raw local socket client.

| Provider | Chat endpoint | Schema requirement |
|---|---|---|
| Groq | `https://api.groq.com/openai/v1/chat/completions` | GPT-OSS 20B/120B and Qwen 3.8 27B currently support `response_format.type=json_schema`, `strict:true`. All object properties must be required and `additionalProperties:false`; supported schema subset applies. Structured outputs currently exclude streaming/tool use. [Compatibility](https://console.groq.com/docs/openai), [schema documentation](https://console.groq.com/docs/structured-outputs). |
| Cerebras | `https://api.cerebras.ai/v1/chat/completions` | Public GPT-OSS 120B/Qwen 3.8 27B support strict JSON schema. Objects require `additionalProperties:false`; the documented schema subset and size/depth bounds apply. Use explicit model and completion/reasoning limits. [Compatibility](https://inference-docs.cerebras.ai/resources/openai), [schema documentation](https://inference-docs.cerebras.ai/capabilities/structured-outputs). |
| OpenRouter | `https://openrouter.ai/api/v1/chat/completions` | Support and strictness are endpoint-specific. Send the schema and `require_parameters:true`; confirm that the pinned provider implements constrained decoding rather than merely treating the schema as a hint. [Structured outputs](https://openrouter.ai/docs/guides/features/structured-outputs), [routing](https://openrouter.ai/docs/guides/routing/provider-selection). |

The inspected integration points are:

- [LocalModelClient.php](../src/Core/LocalModelClient.php), `complete:64` / `request:115`: sends messages and a strict schema, parses `choices[0].message.content`, returns proposal plus usage, and bounds response bytes. Its transport is plain TCP, has no authentication, does not send a model ID, uses a llama.cpp-specific `cache_prompt`, and assumes `/health`. Changing its host variable to a cloud address would be incorrect. Preserve this local boundary; add a separate authenticated HTTPS client if authorized.
- [LocalModelWorker.php](../src/Core/LocalModelWorker.php), `proposalSchema:166`, `runOnce:32`: reuse schema definitions and the fenced claim → completion → finish → integration lifecycle. The worker has a concrete `LocalModelClient` type and a local health/cooldown/model identity, so a cloud implementation requires a deliberate adapter/worker seam. A cloud response can still violate semantic evidence requirements even if its JSON conforms.
- [FreeModelWorker.php](../src/Core/FreeModelWorker.php), `runOnce:38`, `discoverModels`, `invokeModel`: this is an OpenCode CLI lane pinned to `opencode/*-free`, not an existing generic Groq/Cerebras/OpenRouter HTTP client. Discovery refreshes executable/runtime state and was not invoked for this read-only research. Its deny-all tool policy, maximum three attempts, bounded deadline, and integration fencing are useful patterns; widening the free-model regex is not a complete integration.
- [OpenCodeQuota.php](../src/Core/OpenCodeQuota.php), `acquire`, `rateLimited`, and [ModelRateLimit.php](../src/Core/ModelRateLimit.php): reusable concepts are provider-wide admission, persisted cooldown, and `Retry-After`. The existing classes and error text are OpenCode-specific. A cloud lane should honor each provider's organization-wide token/request limits and defer work without treating a 429 as evidence failure.

Targeted searches in `src`, `config`, and `bin` found no existing Groq/Cerebras/OpenRouter-specific integration. No credential files or environment values were needed to establish these seams. Existing account access is therefore unknown, not absent.

## Conservative implementation and measurement plan

1. **Start with a synthetic fixture runner outside the live executive.** Use hand-authored tasks and the existing proposal schemas, with no private memories, workspace projection, repository secrets, or live tool results. Pin provider/model/reasoning settings. A proposed pilot budget is 20 calls, maximum 2,048 input and 512 total completion tokens each, concurrency one; permit it only against confirmed no-charge authorized access while spending remains unresolved.
2. **Measure complete useful proposals.** Record monotonic request-to-validated-proposal duration, token usage including reasoning, HTTP status, finish reason, schema validity, independently checked correctness, and all retry costs. Compare against the same synthetic local tasks. Groq advertises roughly 500 tokens/s and Cerebras roughly 3,000 for GPT-OSS 120B, but neither establishes time-to-first-token or end-to-end p95 here. A 20-call pilot is only a screening sample; it does not establish a reliable production p95. [Groq model page](https://console.groq.com/docs/model/openai/gpt-oss-120b), [Cerebras catalog](https://inference-docs.cerebras.ai/models/overview).
3. **Use a provider-specific HTTPS implementation, if selected.** Require certificate verification, a host allowlist, a secret supplied by the service environment rather than command arguments, a hard wall deadline, bounded response bytes, non-streaming JSON, explicit completion/reasoning budgets, and sanitized errors. Never send tools or select an agentic compound endpoint. Reject truncation/refusal/malformed proposals before integration; retain all executive validators.
4. **Add admission before claiming production work.** Check an explicit allowlist of externally approved work types/data scopes and provider budget availability. A shared account budget must include retries and multiple lanes. Exceeding quota should queue/defer; privacy or spending restrictions must not silently relax during fallback. Keep local-only work local.

A provider passes the initial screen only if it returns useful valid proposals on the synthetic tasks, improves completed-call latency over the local baseline, and fits the explicitly approved cost/egress envelope. No provider has yet passed that screen in this investigation. The immediate deliverable is this evidence-backed choice and integration plan; implementation, enrollment, spending, and production routing remain separate decisions.
