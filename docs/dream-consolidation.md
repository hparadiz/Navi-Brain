# Bounded dream consolidation

The optional dream coordinator runs local `NativeMaintenance` upkeep, then an explicitly enabled, privacy-authorized OpenCode consolidation lane. It does not invoke `sleep()`, narrative generation, public reflection, or general work scheduling. The default permits one OpenCode CLI invocation per 5400 seconds; an explicit cap of two permits a second distinct batch only on the same live coordinator stack after the first batch is accepted. `accepted_batch` means first completion of a grounded batch, including exact reuse of an existing semantic claim. It does not attest creation of a new native record; `new_assertion` remains conservative.

Reported per-row maintenance failures remain visible in the combined result and activate worker error backoff, but do not suppress a due dream admission. One unrelated broken projection must not permanently starve eligible episodic evidence. A thrown maintenance failure still aborts the pass; dream preparation independently checks its own source, ledger, lease, pause and quota state.

`ExecutiveCore::prepareDreamConsolidation` divides its source-ingestion budget between an ascending history page and a newest episodic tail: the default 32 permits 16 of each. Odd limits favor the ascending half; a limit of one alternates history and tail across selection turns. A durable singleton cursor starts at zero, never the ledger maximum. The ascending page's inserts and cursor compare-and-swap share one SQLite commit; tail inserts never move that cursor. Unique ledger inserts preserve previous outcomes. Foreground synchronization uses the same bounded ascending helper with a 100-record page, replacing its former initial corpus scan.

Three preparation opportunities seed from newest pending evidence, then one seeds from an oldest pending page. The historical page rotates beyond oversized or duplicate evidence using its own durable cursor. The durable four-phase turn advances even when selection is quiet, so an oversized historical page cannot trap future fresh selection; existing leases and transport retries do not advance it. A current bounded tail cannot guarantee immediate admission of every arrival if more sources arrive than its size. The independent ascending cursor eventually covers the intervening history without holes caused by tail admission.

The pending selection, queued-assignment recovery and dedicated-work recovery each have their own 32-row bound; these are separate bounds, not a 32-record total across preparation. Each historical traversal persists its position, including runs started with `--once`. Page selection and position advancement share one SQLite transaction; native processing follows commit. The work-lane cursor advances over every selected ID before filtering status. A crash may defer a selected page until wraparound, but restarting does not reset every scan to its first page. An empty page resets its cursor for the next pass. These traversal positions are not claims that evidence was processed successfully. Continuous append can delay wraparound, so this is no strict recovery-latency guarantee; row limits also do not bound all per-batch integration work. Native source observations precede the dream assignment transaction. Quiet polling is throttled in the coordinator; persistent provider reservation independently governs actual inference admissions.

A batch contains at most 12 coherent fresh sources. The prompt preserves the existing evidence projection through JSON encoding, without prose sanitization: generic episode text currently projects its first 800 characters; machine/action episodes project their observed command results. Entire projected sources are included or omitted to keep the prompt within 16384 bytes. Omitted oversized IDs are reported and remain pending. No optional comparison episodes are included in this initial bounded lane. Similarity selects related evidence, but duplicate suppression compares exact projected-byte SHA-256 hashes, preserving case, punctuation, quantities and negation differences.

New `dream-consolidation-v2` jobs store a short protocol marker, ordered native memory IDs, per-source projected hashes, renderer/projection versions and the rendered prompt hash. Source prose remains in native token memory. Immediate dispatch can reuse the ephemeral prompt produced by preparation after matching the exact claimed manifest; this preserves the existing preparation-to-dispatch observation gap. A resumed job reconstructs at most twelve sources neutrally, preserving their original order and verifying eligibility, per-source hashes and the complete rendered prompt before reserving an inference attempt. A source change cancels only the exact leased batch and resets its owned ledger entries. Transport failure or an unsupported renderer leaves the work recoverable without spending a provider reservation. Stored v1 prompts remain supported; v1-only workers cannot interpret v2 marker work as a valid prompt.

The lease and immutable work manifest are checked again after reconstruction, with at least 100 seconds remaining before admitting the bounded 90-second request. This is headroom at admission, not a wall-time guarantee through later filesystem or scheduling delays. A subsequent pause check still fences transmission. Reference storage saves at most 16 KiB of retained prompt prose per job before database overhead; cold reconstruction can fetch much larger complete native records. No latency improvement is inferred from the storage saving.

Every fresh source, including sources the model rejects, is neutrally re-read and checked for active episodic status, unexpired TTL and its queued evidence hash before changing ledger outcomes. Supported sources reuse these observations. A changed evidence version is requeued with attempts reset; an old response cannot exhaust the new version's attempt allowance. The existing literal/lexical grounding validator remains a necessary filter, not a semantic entailment proof. Generated claims never automatically supersede another memory.

The dream bootstrap recognizes only direct `source_memory_id` semantic provenance as prior coverage. Event identity alone cannot establish that a claim covers every episode derived from that event. The shared foreground/dream ingestion helper also uses direct source-memory provenance; neither shared bootstrap path now treats event identity alone as claim coverage. Direct provenance also lacks a historical source-version hash: this mechanism does not by itself reopen already-consolidated ledger entries after arbitrary in-place edits behind its ID cursor.

Queued dream work is isolated from general model workers by the dedicated work-lane table. An expired lease reaches the exact-work claim recovery path; a live lease cannot be resent. Completed-work recovery replays the stored proposal without inference. It also handles a crash after `addMemory` commits the primary source ledger but before the final consolidation event, using the deterministic operation receipt and matching source/semantic identities. A first accepted batch is distinguished from replay inside the final SQLite transaction by an indexed event deduplication key. SQLite ownership does not make native memory and the executive store one atomic system.

The pending-work lookup has a partial `(work_type,id)` index restricted to queued/leased jobs. Its exact status predicate and ordered ID lookup keep completed history and unrelated work types out of this recurring query. Index eligibility was reviewed from source; no live query-plan or latency measurement was performed.

`memory:consolidation:status` reports the durable ascending cursor. `unscanned_active_episodes` counts native active records above it; some may already be tracked through tail admission, so this is also labeled `untracked_upper_bound`. `scanned_active_episodes` describes the scanned prefix. The old exact-looking `tracked_active_episodes` and `untracked_active_episodes` fields are retained as null rather than publishing a false anti-join count; ledger status counts remain separate.

Local source inspection and PHP lint support these contracts. The original queue implementation was reviewed without live provider calls or behavioral tests. The subsequent Muse CLI transport was verified with a public invented example; see the transport contract for measured results and its pending private-memory approval. See [the transport contract](opencode-dream-transport.md) and [native maintenance](native-maintenance.md) for provider and projection limits.
